## 🔢 Scrum 33355（必背第一优先级）

```
3 大支柱 ：透明 → 检视 → 适应      （因果链，缺一不可）
3 个角色 ：Developers、Product Owner、Scrum Master
3 个工件 ：Product Backlog、Sprint Backlog、Increment
5 个价值观：承诺、专注、开放、尊重、勇气
5 个事件 ：Sprint、Sprint Planning、Daily Scrum、Sprint Review、Sprint Retrospective
```

---

## 📌 核心概念一句话速记

| 概念 | 一句话 |
|------|--------|
| Scrum | 不是过程/技术，是**框架**（容器），框架内可应用各种流程和技术 |
| 经验主义 | 知识源自实际经验，非先天观念或纯理性推理 |
| 精益思维 | 减少浪费，专注根本（第一性思维） |
| 跨职能 | 团队具备端到端交付所需**全部技能**，不等于人人全栈 |
| 自管理 | 团队内部决定谁做什么、何时做、如何做 |
| Sprint | 固定时长 ≤ 1 个月的容器型事件，通常 **2 周** |
| Story Point | **相对**估算单位，不是绝对时间 |
| 用户故事 | 是**占位符**，不是完整需求文档 |

## 👥 三个角色职责对比

| | Developers | Product Owner | Scrum Master |
|--|-----------|---------------|-------------|
| 核心职责 | 创建可用 Increment | 产品价值**最大化** | 建立 Scrum，对团队**效能**负责 |
| 管什么 | Sprint Backlog、质量注入、每日调整 | Product Backlog（排序、沟通、透明） | 框架实施、移除障碍 |
| 关键约束 | 对彼此负责 | **是一个人不是委员会** | 服务式领导（Servant Leader） |
| 决定什么 | 估算（Estimate） | 范围 + 重要性 | 过程和规则 |

## 📝 用户故事速查

### 模板
```
作为 <某类用户>，我想 <做某事>，从而 <创造某些价值>。
```

### 3C 原则（Ron Jeffries）
- **C**ard（卡片）— 占位符
- **C**onversation（交谈）— 深入讨论
- **C**onfirmation（确认）— 完工条件

### INVEST 原则
```
I - Independent    独立性
N - Negotiable     可协商
V - Valuable       有价值
E - Estimable      可估算
S - Small          短小
T - Testable       可测试
```

### DoD vs 验收标准

| | DoD（Definition of Done） | 验收标准（Acceptance Criteria） |
|--|--------------------------|-------------------------------|
| 范围 | 团队通用，适用于**所有**故事 | 单个故事特定 |
| 内容 | 质量标准（测试、集成、文档…） | 功能行为（Given-When-Then） |
| 谁定 | 团队共同制定 | PO + 团队讨论 |

## 🃏 估算方法对比

| 方法 | 特点 | 适用场景 |
|------|------|----------|
| **计划扑克** | 斐波那契卡片，独立出牌，讨论差异 | 最常用，中等规模 Backlog |
| **T 恤尺码** | S/M/L 快速分类 | 快速粗估 |
| **卡片队列法** | 逐张比较相对大小排列 | 大量条目快速排序 |
| **"金发女孩"** | 分割/组合到大致相当规模 | 规模标准化 |

## ⚔️ Scrum vs XP（易考对比）

| 维度 | Scrum | XP |
|------|-------|----|
| 关注点 | 项目管理、团队过程 | **工程实践**、代码质量 |
| 技术实践 | **无** | TDD、结对编程、重构、持续集成… |
| 关系 | 框架/容器 | 填充 Scrum 的技术实践 |

> "没有 XP 实践的支撑，Scrum 难以成功"

---

## 🏢 大规模敏捷对比（SAFe vs LeSS）

| 维度 | SAFe | LeSS |
|------|------|------|
| 理念 | 分层扩展，增加角色和流程 | "LeSS **is** Scrum"，极简扩展 |
| 创建者 | Dean Leffingwell (2011) | Craig Larman |
| 核心概念 | ART（5-12 团队的发布列车）、PI | 1 个 PO + 1 个 Backlog + 统一 Sprint |
| 适用规模 | 大型企业（数百人） | 2-8 团队（基本）/ 8+ 团队（Huge） |
| 复杂度 | 高（四层架构、多角色） | 低 |
| 常见批评 | "披着敏捷外衣的瀑布" | "过于理想化" |

## 🔺 三大支柱因果链（易考简答/选择）

```
透明   →   检视   →   适应
 │           │          │
 │           │          └─ 超出范围时尽快调整
 │           └─ 频繁勤勉地审查，发现偏差
 └─ 过程和工作对所有人可见
 
⚠️ 没有透明的检视 → 产生误导和浪费
⚠️ 没有适应的检视 → 毫无意义
```

## 🐷🐔 猪与鸡（易考理解题）

| 角色 | 投入程度 | 对应 Scrum | 在项目中 |
|------|----------|-----------|---------|
| 猪 | **全身投入**（Committed） | PO、SM、Developers | 参与决策 |
| 鸡 | **仅参与**（Involved） | 用户、客户、经理 | 排除在决策之外 |

## 🔄 Scrum Guide 2020 变更要点

| 变更 | 旧版 | 新版 |
|------|------|------|
| 团队称谓 | "开发团队" | "开发者"（去掉子团队概念） |
| 目标体系 | 无明确层级 | Product Goal → Sprint Goal → DoD 三层 |
| 每日站会 | 固定三问 | 取消固定格式，聚焦进度与障碍 |
| 指南篇幅 | 较长 | 删减 50%，强调适应性 |

## 📐 Sprint 三变量

```
        范围 (Scope)
       /           \
      /    质量不在   \
     /    三变量中     \
重要性 ——————————— 估算
(Importance)      (Estimate)

PO 设置：范围 + 重要性
团队设置：估算

内部质量必须最好，外部质量可以简陋一些
```

## ⏱ Daily Scrum 两种模式

| 传统三问模式 | 看板遍历模式 |
|------------|------------|
| 关注**人** | 关注**事**（接力棒） |
| 昨天做了什么 / 今天做什么 / 有什么障碍 | 遍历看板墙，检查工作流流动 |
| 2020 前常用 | 2020 后推荐 |
