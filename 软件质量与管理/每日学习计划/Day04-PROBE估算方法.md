# Day 4：PROBE 估算方法

> 预计用时：30分钟 | 考频：★★★★★

---

## 一、估算的本质

- 估算是在**预测未来**，经常是错误的（误差巨大）
- 但估算过程**仍然有用**：管理不确定性、发现误解和不一致、建立对工作的一致理解
- **收益递减原则**：不应花太多时间在估算上

### 为什么可以用历史数据完成规模估算？
> 因为使用代理规模与实际程序规模之间的关系完成规模估算，**规模估算产生偏差的原因相对客观**，偏差可以用来修正新的估算结果。

### 为什么时间估算的偏差更复杂？
> 一方面和**规模**有关，另一方面跟**人的主观能动性**有关。因此时间估算偏差产生的原因可能是估算结果本身，这使得历史数据中时间偏差可参考价值不大。

---

## 二、PROBE 方法的基本原理（2020-mid 4分）

### 两个核心原理

```
1. 设立合理的代理作为精确度量和早期规划需要的度量之间的桥梁
2. 使用相对大小而非绝对大小
```

> **PROBE** = PROxy Based Estimation（基于代理的估算）

---

## 三、PROBE 方法的过程（2020-mid 4分，需画流程图）

```
        ┌────────────┐
        │  概要设计    │
        └──────┬─────┘
               ↓
    ┌─────────────────────┐
    │ 代理识别和代理规模(E) │
    └────┬───────────┬────┘
         ↓           ↓
┌──────────────┐ ┌──────────────┐
│估算并调整程序规模│ │估算并调整资源  │
└──────┬───────┘ └──────┬───────┘
       ↓                 ↓
┌──────────────┐ ┌──────────────┐
│ 计算预测区间   │ │ 计算预测区间   │
└──────────────┘ └──────────────┘
```

### 估算过程详解

1. **概要设计**：确认产品功能，明确所需的程序组件/模块
2. **代理识别和代理规模**：将组件/模块与之前缩写的程序序比较，估算规模，得到总规模
3. **估算并调整程序规模**（左路）：用线性回归方法
4. **估算并调整资源**（右路）：用线性回归方法
5. **计算预测区间**：给出置信区间

### 估算要点
- 尽可能划分详细一些
- 建立对结果的信息
- 依赖数据
- **估算关注的是过程而不是结果**

## 四、PROBE ABCD 方法（2020-mid 10分大题 必考！）

### 估算规模时的数据质量要求

| PROBE方法 | 数据要求 | 数据质量要求 | 计算方法 |
|----------|---------|-----------|---------|
| **A** | 3组或3组以上**代理规模(E)**与**实际程序规模**数据 | r≥0.7; s≤0.05; β0≤估算结果的25%; 0.5≤β1≤2 | 线性回归 |
| **B** | 3组或3组以上**计划程序规模**与**实际程序规模**数据 | r≥0.7; s≤0.05; β0≤估算结果的25%; 0.5≤β1≤2 | 线性回归 |
| **C** | 有历史数据 | 无质量要求 | **按比例调整** |
| **D** | 没有历史数据 | 无 | **猜测** |

### 估算时间时的数据质量要求

| PROBE方法 | 数据要求 | 数据质量要求 | 计算方法 |
|----------|---------|-----------|---------|
| **A** | 3组或3组以上**代理规模(E)**与**实际开发时间** | r≥0.7; s≤0.05; β0显著小于估算结果; β1≤0.5×(历史生产效率的倒数) | 线性回归 |
| **B** | 3组或3组以上**计划程序规模**与**实际开发时间** | r≥0.7; s≤0.05; β0显著小于估算结果; β1≤0.5×(历史生产效率的倒数) | 线性回归 |
| **C** | 有历史数据 | 无 | **按比例调整** |
| **D** | 没有历史数据 | 无 | **猜测** |

### 评分标准
> A、B 都是 **3分**，C和D 都是 **2分**

### 参数含义

| 参数 | 含义 |
|------|------|
| **r** | 相关性（两组数据之间互相关联的程度），PSP要求 **r ≥ 0.7** |
| **s** | 显著性（两组数据的相关关系出现的偶然性），PSP要求 **s ≤ 0.05** |
| **β0** | 回归截距 |
| **β1** | 回归斜率 |

## 五、为什么不使用生产效率数据？（2020-mid 2分）

> 在估算资源需求（例如人时）的时候，生产效率一般在**分母**上。考虑到个体软件工程师**生产效率波动**，容易导致估算偏差范围变大。

---

## 六、规模度量标准

选择度量方式的四个要求：
1. 必须反映开发成本
2. 必须精确
3. 必须能用**自动化方法**来统计
4. 必须有助于早期规划

### 规模度量方法对比（LOC vs FP）

| 方法 | 优点 | 缺点 |
|------|------|------|
| **LOC** | 是软件开发项目的生成品，容易进行计算 | 依赖程序设计语言(不同语言有偏差)；对代码量少但设计精巧的程序不利；不适合非过程语言；开发初期估算代码行数困难 |
| **FP** | 和程序设计语言无关；面向过程和非过程语言均适合；基于项目开发初期就可能得到的数据 | 计算基于主观而非客观数据 |

> 随着软件产业化分工，基于LOC的度量方式逐渐失去意义，而基于FP的度量方式显得更加符合要求。

## 七、线性回归方法要点

```
Plan Size = β0 + β1 × size(E)
Plan Time = β0 + β1 × time(E)
Range = t(p,df) × σ₁ × √(1 + 1/n + ...)
```

### 处理有限的历史数据

规模估算的四种方法（从简单到复杂）：
1. **简单方法**：VS=min, S=VS+M/2, M=median, L=M+VL/2, VL=max → 计算简单但不稳定
2. **正态分布法**：VS=M-2σ, S=M-σ, L=M+σ, VL=M+2σ → 相对稳定
3. **对数正态分布法**：先取对数，按正态分布法计算，再取反对数 → 符合直觉（大多数人写小程序多，大程序少）
4. **线性回归方法**：利用相关性进行预测

# CodeX回答

下面按考试和理解两条线来讲 PROBE。

**1. PROBE 是什么**

PROBE = `PROxy Based Estimation`，即“基于代理的估算方法”。

它解决的问题是：项目早期我们还不知道最终代码行数、工时、缺陷数，但又必须做计划。于是 PROBE 找一个早期可识别、又和最终规模相关的“代理对象”，用它来推断最终规模和资源。

比如：

| 真正想估的东西 | 早期不容易直接知道 | 可用代理 |
|---|---|---|
| 最终代码规模 LOC | 还没写代码 | 类、方法、模块、页面、接口、功能点 |
| 开发工时 | 人还没开始做 | 代理规模、计划规模 |
| 测试/评审工作量 | 缺陷未知 | 规模、历史缺陷密度、历史工时 |

所以 PROBE 的核心不是“拍脑袋估代码行”，而是：

> 先估一个早期能看见的代理规模，再用历史数据把代理规模映射到实际规模或资源。

---

**2. 两个核心原理**

PROBE 有两个基本原理，考试很爱考：

1. **设立合理代理**  
   用代理对象作为“早期规划需要的度量”和“最终精确度量”之间的桥梁。  
   例如早期能看到“有 5 个页面、12 个 API、3 个复杂模块”，后期能精确统计 LOC 和工时。

2. **估相对大小，而不是绝对大小**  
   人直接估“这个模块 437 行代码”很难，但比较“这个模块比上次那个登录模块大一些，应该是 L 级”更容易。  
   所以 PROBE 常把组件分成 `VS / S / M / L / VL`，即非常小、小、中、大、非常大。

---

**3. PROBE 的基本流程**

可以记成这条线：

```text
概要设计
  ↓
识别代理对象并估算代理规模 E
  ↓
 ┌───────────────┬───────────────┐
 ↓               ↓
估算并调整程序规模  估算并调整资源
 ↓               ↓
计算预测区间       计算预测区间
```

展开解释：

1. **概要设计**  
   先把系统拆成模块、类、页面、接口、组件等。没有拆分就无法估算。

2. **识别代理对象**  
   选择和最终工作量强相关的对象。  
   面向对象项目可用类、方法；Web 项目可用页面、API、组件；文档工作可用页数。

3. **估代理规模 E**  
   参考历史项目，把每个代理对象归类为 `VS/S/M/L/VL`，再换算为一个代理规模值。

4. **估算并调整程序规模**  
   如果历史数据质量足够，可以用线性回归：

   ```text
   计划规模 = β0 + β1 × 代理规模 E
   ```

5. **估算并调整资源**  
   同理，可以估开发时间、人时、测试工作量：

   ```text
   计划时间 = β0 + β1 × 代理规模 E
   ```

6. **计算预测区间**  
   不只给一个点估计，还要给出可能误差范围。  
   例如“预计 5000 LOC，80% 置信区间为 4200-5800 LOC”。

---

**4. PROBE A/B/C/D 四种方法**

PROBE 根据历史数据质量分成 A、B、C、D。越靠前越可靠。

| 方法 | 使用条件 | 做法 | 可靠性 |
|---|---|---|---|
| PROBE A | 有 3 组以上“代理规模 E 与实际规模/实际时间”数据，且质量合格 | 用线性回归 | 最高 |
| PROBE B | 没有好的代理规模数据，但有 3 组以上“计划规模与实际规模/时间”数据，且质量合格 | 用线性回归 | 较高 |
| PROBE C | 有历史数据，但质量不满足 A/B | 按比例调整 | 一般 |
| PROBE D | 没有历史数据 | 猜测、专家判断 | 最低 |

规模估算时，A/B 的数据质量要求常考：

```text
r ≥ 0.7
s ≤ 0.05
β0 ≤ 估算结果的 25%
0.5 ≤ β1 ≤ 2
```

含义是：

| 参数 | 含义 |
|---|---|
| r | 相关系数，表示代理规模和实际规模是否强相关 |
| s | 显著性，通常理解为相关关系不是偶然产生的概率指标 |
| β0 | 回归截距，不能太大，否则说明估算被固定偏移量主导 |
| β1 | 回归斜率，不能太离谱，否则说明历史关系不稳定 |

---

**5. 为什么时间估算比规模估算更难**

规模估算主要受模块复杂度、功能数量、技术形态影响，偏差原因相对客观，所以历史数据比较有用。

但时间估算还受人的状态影响，例如：

- 熟练程度不同
- 中途被打断
- 需求变化
- 调试困难
- 团队协作成本
- 主观能动性和投入程度

所以课上会强调：

> 估算本质上是预测未来，不可能完全准确。估算追求的不是绝对正确，而是一致性，以及让使用估算结果的人有信心。

---

**6. 为什么不直接用生产效率估时间**

看起来可以这样算：

```text
开发时间 = 规模 / 生产效率
```

但问题是，生产效率在分母上。分母轻微波动，会导致结果大幅变化。

例如：

```text
规模 = 1000 LOC
效率 = 100 LOC/小时 → 10 小时
效率 = 50 LOC/小时  → 20 小时
效率 = 25 LOC/小时  → 40 小时
```

效率只变了几倍，时间估算就可能翻倍甚至更多。个人软件工程师的效率波动又很大，所以直接用历史生产效率估时间风险较高。

---

**7. PROBE 的优缺点**

优点：

- 有明确过程，不是纯拍脑袋。
- 能利用历史数据修正估算。
- 能让估算结果更一致。
- 能给出预测区间，增强计划可信度。
- 适合 PSP/TSP 中个人或团队过程改进。

缺点：

- 非常依赖高质量历史数据。
- 新团队、新技术栈、新领域时历史数据可能失效。
- 代理对象选错会导致估算偏差。
- 初期分类 `VS/S/M/L/VL` 仍然带有主观性。
- 小样本回归容易不稳定。

---

**8. 考试版答案模板**

如果论述题问“解释 PROBE 方法”，可以这样答：

```text
PROBE 是 Proxy Based Estimation，即基于代理的估算方法。其基本思想是在项目早期选择合理的代理对象，作为早期规划所需度量和最终精确度量之间的桥梁，并通过相对大小而非绝对大小进行估算。

其过程为：首先进行概要设计，识别系统中的模块、类、方法或其他代理对象；然后根据历史数据估算代理规模 E；接着分别估算并调整程序规模和资源需求；最后计算预测区间，给出估算结果及其置信范围。

PROBE 根据历史数据质量分为 A、B、C、D 四类。A 使用代理规模与实际规模/时间的高质量历史数据进行线性回归；B 使用计划规模与实际规模/时间的高质量历史数据进行线性回归；C 有历史数据但质量不足，按比例调整；D 没有历史数据，只能猜测或专家判断。
```
