## 一、DevOps（2016、2021 考题）

### 定义
> DevOps = Development + Operations
> 是一组过程、方法与系统的统称，用于促进开发、技术运营和质量保障部门之间的**沟通、协作与整合**。

### DevOps 三个步骤（2016 真题）

1. **持续集成**（Continuous Integration）
2. **持续交付**（Continuous Delivery）
3. **持续部署**（Continuous Deployment）

### DevOps 的特点（2018 真题）

| 特点 | 说明 |
|------|------|
| **为什么流行？** | 随着互联网的发展，软件产品类型和用户规模发生了重大变化，需要更快的迭代速度 |
| **相关重要概念** | 云基础设施、微服务架构、持续集成、持续交付 |

### DevOps 精益思想（2018 真题）

从左往右依次**快速调整**的过程：

```
开发 → 测试 → 运维 → DevOps
  ↓      ↓      ↓       ↓
价值  用户需求  真实反馈  价值传递
```

> 开发在左，运维在右。后将开发过程和运维过程共同拉动，让真正的业务价值顺畅流动起来，为企业持续创造价值。

## 二、持续集成（2016、2021）

### 关键实践（2021 考题）

1. **维护单一的源代码库**
2. **自动化构建**
3. **构建自测试**
4. **每个人每天都向主干提交代码**
5. **每次提交都要在持续集成机器上构建**
6. **保持快速构建**
7. **在与生产环境尽可能一致的环境中测试**
8. **让任何人都能获得最新的可执行版本**
9. **保证构建结果对所有人可见**
10. **自动化部署**

### IT及对生产关系的影响（2018 真题）

> 随着企业对IT的依赖越来越深，IT部门和业务部门之间的边界在逐渐消失。技术和业务的融合使得DevOps成为必然。

## 三、配置管理

### 配置管理的活动

1. **配置标识**：确定哪些项目需要纳入配置管理
2. **配置控制**：管理配置项的变更
3. **配置状态报告**：记录和报告配置项的状态
4. **配置审计**：验证配置的完整性和一致性

### 配置管理的目标

- 确保软件开发过程中的**一致性**和**可追溯性**
- 支持**并行开发**和**版本控制**
- 便于**问题追踪**和**回滚**

## 四、GQM（Goal-Question-Metric）方法

### 定义
> GQM是一种自上而下的度量方法，从**目标**出发，通过**问题**分解，最终确定需要收集的**度量指标**。

### GQM 三层结构

```
        Goal (目标层)
          /    \
    Question  Question (问题层)
      /  \      /  \
   Metric Metric Metric (度量层)
```

### GQM 应用步骤

1. **确定目标**：明确度量的目的（提高质量、缩短周期等）
2. **提出问题**：针对目标提出具体问题（当前质量如何？哪里有问题？）
3. **定义度量**：为每个问题确定可度量的指标（缺陷密度、测试覆盖率等）

### GQM 示例

**目标**：提高软件质量

**问题1**：当前缺陷率是多少？
- 度量1：每千行代码缺陷数
- 度量2：测试阶段发现的缺陷数

**问题2**：哪些阶段缺陷注入最多？
- 度量3：各阶段Inject Rate
- 度量4：Phase Yield

## 五、根因分析（Root Cause Analysis）

### 定义
> 找出问题的**根本原因**而非表面现象，从源头消除问题。

### 常用方法

1. **5 Why分析法**：连续问5次"为什么"，挖掘根本原因
2. **鱼骨图（Ishikawa Diagram）**：从人、机、料、法、环等维度分析
3. **帕累托分析（80/20法则）**：找出影响最大的20%因素

### 在PSP/TSP中的应用

- 通过**缺陷记录**分析缺陷产生的根本原因
- 制定**预防措施**避免同类缺陷再次发生
- 持续改进开发过程

## 六、V&V（Verification and Validation）

### 定义

| 概念 | 英文 | 问题 | 关注点 |
|------|------|------|--------|
| **验证** | Verification | Are we building the product **right**? | 产品是否符合**需求规格说明** |
| **确认** | Validation | Are we building the **right** product? | 产品在**实际环境**中是否能正确工作 |

### 区别

- **验证**：检查软件是否符合设计规格（内部一致性）
- **确认**：检查软件是否满足用户需求（外部适用性）

### V&V 活动

- **验证活动**：评审、检查、测试（单元测试、集成测试）
- **确认活动**：系统测试、验收测试、用户试用

## 📌 通俗详解：DevOps + 持续集成 + 配置管理到底在解决什么问题？

### 1. 先用一句话理解

DevOps、持续集成、配置管理看起来是三个概念，其实都围绕一个核心目标：

> 让软件从“写出来”到“可靠地交到用户手里”这条路更短、更稳、更可追踪。

传统开发里常见的问题是：
- 开发说“我本地能跑”
- 测试说“你一合并就坏”
- 运维说“上线环境和你们开发环境完全不一样”
- 项目经理说“到底现在上线的是哪个版本？”

DevOps解决协作问题，持续集成解决频繁合并和快速发现问题，配置管理解决版本、变更和可追溯问题。

---

### 2. DevOps：把开发、测试、运维拉到同一条价值流上

DevOps不是某一个工具，也不是“会用Docker/Jenkins就叫DevOps”。它更像一种组织和工程文化：

> 开发、测试、运维不再各做各的，而是围绕用户价值共同负责。

传统模式像接力赛：

```
开发写完 → 扔给测试 → 测试测完 → 扔给运维 → 运维上线
```

问题是每一棒之间都会丢信息、丢责任、丢反馈。DevOps更像流水线加反馈回路：

```
开发 → 构建 → 测试 → 交付 → 部署 → 监控 → 反馈 → 再开发
```

它强调：
- **快**：需求变化后能快速响应
- **稳**：快不是乱快，要靠自动化和规范保证质量
- **通**：开发、测试、运维、业务之间的信息要流动
- **反馈**：真实用户和运行环境的反馈要回到开发过程

考试里问“为什么DevOps流行”，可以从这几个角度答：

1. 互联网产品迭代速度快，不能半年一年才上线一次。
2. 用户规模大，线上问题影响范围更大，需要快速修复和回滚。
3. 云计算、容器、微服务等技术让自动化部署和弹性运维成为可能。
4. 开发和运维边界模糊，软件交付变成持续过程而不是一次性交付。

---

### 3. CI、持续交付、持续部署的区别

这三个词很容易混。可以按“自动化推进到哪一步”来记：

| 概念 | 自动化到哪里 | 是否自动上线到生产 | 重点 |
|------|--------------|--------------------|------|
| **持续集成 CI** | 自动构建、自动测试 | 否 | 频繁合并，尽早发现集成问题 |
| **持续交付 CD** | 生成可发布版本 | 通常需要人工批准 | 随时可以发布 |
| **持续部署 Continuous Deployment** | 自动发布到生产环境 | 是 | 每次通过流水线都可自动上线 |

最简单的记忆：

> CI保证“代码合得上”，持续交付保证“版本发得出”，持续部署保证“通过就上线”。

---

### 4. 持续集成为什么重要？

持续集成的核心不是“有一台CI服务器”，而是：

> 大家频繁把代码合到主干，每次合并都自动构建和测试，尽早发现冲突和缺陷。

如果每个人都在自己的分支上写两周，最后再一起合并，就会出现“集成地狱”：

- A改了接口，B还按旧接口调用
- C改了配置，D本地环境跑不起来
- 测试直到最后一天才发现基础功能坏了

持续集成把大问题拆成小问题：

- 每次只合一点代码
- 每次都自动编译、测试
- 一坏马上知道是谁的提交引入的
- 修复成本低，团队也更敢改代码

---

### 5. 持续集成10条实践的理解版

| 实践 | 通俗解释 | 为什么重要 |
|------|----------|------------|
| 单一源代码库 | 所有正式代码放在统一仓库 | 避免“哪个版本是真的” |
| 自动化构建 | 一条命令或流水线完成构建 | 避免人工步骤出错 |
| 构建自测试 | 构建后自动跑测试 | 不只看能不能编译，还看功能是否坏 |
| 每天提交主干 | 小步提交、频繁合并 | 避免长期分支冲突 |
| 每次提交都构建 | 每个变更都接受检查 | 快速定位问题来源 |
| 快速构建 | 构建不能慢到没人愿意跑 | 反馈越快，修复越快 |
| 类生产环境测试 | 测试环境尽量像线上 | 减少“测试没问题，上线就坏” |
| 最新可执行版本可获得 | 大家都能拿到最新构建产物 | 方便测试、演示、回滚 |
| 构建结果可见 | 失败要让团队知道 | 质量状态透明 |
| 自动化部署 | 减少人工发布步骤 | 降低发布风险 |

考场上不一定要全背一字不差，但最好能写出“源代码库、自动构建、自动测试、频繁提交、快速反馈、可见结果、自动部署”这些关键词。

### 6. 配置管理：给软件开发装上“版本档案系统”

配置管理听起来抽象，其实可以理解为：

> 管好软件项目中所有重要东西的版本、变更、状态和一致性。

这些“重要东西”叫配置项，可能包括：
- 源代码
- 需求文档
- 设计文档
- 测试用例
- 构建脚本
- 配置文件
- 发布包
- 用户手册

如果没有配置管理，就会出现：
- 不知道线上运行的是哪个版本
- 修改了需求但设计和测试没同步
- 修复bug后找不到对应提交
- 发布错包，或者无法回滚

---

### 7. 配置管理四个活动的通俗版

| 活动 | 通俗理解 | 例子 |
|------|----------|------|
| **配置标识** | 先确定哪些东西要管 | 把代码、需求、测试用例列为配置项 |
| **配置控制** | 变更不能随便改，要走流程 | 改需求前提交变更申请并评审 |
| **配置状态报告** | 记录现在每个配置项是什么状态 | 版本号、负责人、是否已发布 |
| **配置审计** | 检查实际内容和记录是否一致 | 发布包是否真的包含已批准的修复 |

一句话背法：

> 标识是“管什么”，控制是“怎么改”，状态报告是“现在怎样”，审计是“有没有对上”。

### 8. GQM：不要为了度量而度量

GQM的意义在于提醒我们：

> 先想清楚目标，再问问题，最后才决定收集什么数据。

很多项目会犯一个错误：看到什么就量什么，比如代码行数、提交次数、测试用例数。但这些数字不一定有意义。

GQM的逻辑是：

1. **Goal**：我想达成什么目标？
2. **Question**：为了判断目标有没有达成，我要回答哪些问题？
3. **Metric**：为了回答这些问题，我需要哪些数据？

例子：

| 层次 | 内容 |
|------|------|
| Goal | 提高交付质量 |
| Question | 缺陷主要在哪个阶段注入？测试是否足够有效？ |
| Metric | 各阶段缺陷注入数、缺陷消除率、测试覆盖率、缺陷密度 |

考试可以这样写：

> GQM是一种目标驱动的度量方法，它从组织或项目目标出发，分解出需要回答的问题，再为问题定义可收集的度量指标，从而保证度量服务于改进目标，而不是盲目收集数据。

---

### 9. V&V：两个英文问题一定要会

V&V最经典的区别：

- **Verification**：Are we building the product right?
- **Validation**：Are we building the right product?

通俗解释：

| 概念 | 关注点 | 例子 |
|------|--------|------|
| **验证 Verification** | 是否按规格正确构建 | 需求说密码至少8位，系统是否真的检查8位？ |
| **确认 Validation** | 产品是否真的满足用户需要 | 用户真正想要快速登录，是否支持扫码/免密等场景？ |

也就是说：

> 验证怕“做错”，确认怕“做偏”。

如果题目问“DevOps是什么以及为什么流行”，可以答：

> DevOps是Development和Operations的结合，是一组促进开发、测试、运维和质量保障之间沟通协作与整合的方法和文化。它强调自动化、快速反馈和价值流动。DevOps流行的原因包括互联网产品迭代速度加快、用户规模扩大、业务与IT边界模糊，以及云基础设施、微服务、持续集成和持续交付等技术的发展。
