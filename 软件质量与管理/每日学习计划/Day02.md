## 一、敏捷宣言（2020-mid 原题：请完整描述敏捷宣言）

### 四个简单的价值观

```
个体和交互      胜过  过程和工具
可以工作的软件    胜过  面面俱到的文档
客户合作        胜过  合同谈判
响应变化        胜过  遵循计划
```

> 也就是说，尽管右项有其价值，我们更重视**左项**的价值。

### 四大特征

## 三、关于敏捷方法的误导性描述（高频！2014、2015A、2016）

> ⚠️ 考试非常喜欢问"哪些对敏捷方法的描述是不合适的"

| 误导性说法 | 为什么不合适 |
|----------|-----------|
| **轻量级方法** | 这是对以XP为代表的一类方法的误导。轻量级和重量级没有具体的区分方法。实际上XP对工程规范有着极为**严格**的要求 |
| **拥抱变更、变更驱动** | 仅仅是口号。对待变更，**所有**软件工程方法都是**限制和管理**的态度。所有正式的项目都是**计划驱动**的，否则计划的作用无法体现 |
| **TDD可以提供更高的开发质量** | 并**没有足够的证据**支持这一观点 |

### 敏捷方法 vs 规范方法：影响选择的五个维度（2014）

> 如果只有强有力的规范而缺乏敏捷，将导致官僚作风停滞不前，团队陷入为了测量而测量的困境
> 如果缺乏创新的敏捷则如同新创公司在盈利之前的不负责任的狂热
> **计划驱动的开发人员必须敏捷，敏捷开发人员必须规范**

## 四、Scrum 框架（33355 必背）

### 记忆口诀：3-3-3-5-5

| 数字 | 内容 | 具体项 |
|------|------|--------|
| **3** 大支柱 | 经验主义基石 | 透明、检视、适应 |
| **3** 个角色 | 团队组成 | 产品负责人(PO)、Scrum Master、开发团队 |
| **3** 个工件 | 可视化产物 | 产品订单(优先级/动态)、冲刺订单(细化/冻结)、燃尽图 |
| **5** 个活动 | 节奏仪式 | Sprint、Sprint Planning、Sprint Daily Standup、Sprint Review、Sprint Retrospective |
| **5** 个价值观 | 文化基础 | 勇气(Coverage)、开放(Openness)、专注(Focus)、承诺(Commitment)、尊重(Respect) |

### 三大支柱因果链
```
透明 → 检视 → 适应
 ↓        ↓       ↓
过程和工作   频繁勤勉    超出范围
对所有人     审查发现    尽快调整
可见         偏差

⚠️ 没有透明的检视 → 产生误导和浪费
⚠️ 没有适应的检视 → 毫无意义
```

## 五、Scrum vs XP（考试常考对比）

| 维度 | Scrum | XP |
|------|-------|----|
| 迭代周期 | **2-4周** | **1-2周** |
| 迭代中需求变更 | 冻结(不允许) | 允许(只要时间资源相同即可变更) |
| 需求优先级 | 比较灵活(可能有需求依赖) | **严格遵守** |
| 过程工程化 | 开发过程**并未工程化** | 对开发流程**严格定义** |
| 关注点 | 项目管理、团队过程 | **工程实践**、代码质量 |

### XP 核心实践
- 客户作为开发团队成员
- 短交付周期
- 结对编程
- 测试驱动开发(TDD)
- 持续集成
- 重构
- 规定每周工作不超过40小时，连续加班不超过2周

## 六、Kanban 方法

- 来源：**精益生产**(丰田制造法)的具体实现
- 核心活动：**可视化工作流、限制WIP(在制品)、管理周期时间**

### Linus 定律
> 如果有足够多的beta测试者和合作开发者，几乎所有问题都会很快显现，然后自然有人会把它解决。

---

## 七、迭代式开发方法

**定义**：大型软件系统的开发过程也是一个逐步学习和交流的过程，软件系统的交付不是一次完成，而是通过多个迭代周期，逐步来交付。

---

## 八、课上选择题中的判断（必记）

| 说法 | 正确/错误 |
|------|---------|
| 软件过程管理是软件项目管理应该要实现的目标 | **错误** |
| 在公司导入敏捷过程是我们今年过程改进的主要目标 | **正确** |
| XP与CMM/CMMI是对立的两种软件开发方法 | **正确**（XP观念确实与严格CMM/CMMI对立） |
| CMM/CMMI不适合当今互联网环境的项目管理需求 | **正确**（是过程管理改进，不是项目管理） |
| PDCA和IDEAL不适合在敏捷环境中使用 | **错误** |
| 不同的软件开发过程应该使用不同的生命周期模型，反之亦然 | **错误** |
