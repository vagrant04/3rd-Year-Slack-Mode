## 一、云计算概念

### 1. 什么是云计算？

云计算目前**没有一个统一权威的定义**，学术界、工业界和标准化组织各有侧重：

- **工业界（强调服务与商业价值）**
  - Google：通过互联网以服务的形式按需提供计算资源。
  - Amazon：通过互联网按需提供 IT 资源，采用**按使用量付费**的定价方式。
  - 华为云：**计算服务能力的网络开放共享**。
- **学术界（强调架构与技术实现）**
  - 刘鹏教授：通过网络**按需提供可动态伸缩的廉价计算服务**。
  - 伯克利技术报告：SaaS + 效用计算（软件应用 + 硬件和系统软件）。
- **标准化权威定义（NIST）**：一种模型，实现对**可配置计算资源共享池**（网络、服务器、存储、应用、服务）的普遍可用、便捷获取与按需网络访问，可概括为**五大特征、三种服务模式、四种部署模式**。

补充术语：**云**指独特的 IT 环境；**IT 资源**是云计算的最小构成单元（计算/存储/平台/应用资源）；拥有 IT 资源≠实现云计算，还需具备**可扩展性**（水平扩展=分配/释放资源；垂直扩展=替换更大/更小容量资源）并封装为**云服务**交付。可把云计算理解为「**效用计算 + 服务计算**」。

（来源：1-云计算概念-2026.pdf 第8-14页、第23页）

### 2. 云计算的特征

NIST 定义的**五大基本特征**：

1. **按需自助服务**：用户按需通过自助界面（控制台、API）自动获取资源，无需人工干预。
2. **广泛的网络访问**：资源可通过标准网络协议被不同设备（笔记本、手机、平板）访问。
3. **资源池化**：计算/存储/网络资源池化，多用户共享同一物理资源，通过逻辑隔离保证安全与隐私。
4. **快速弹性**：资源可根据负载迅速扩展或收缩，高峰低谷均维持高效性能。
5. **可计量服务**：自动监控、控制、优化资源使用，提供透明使用报告与按量计费。

部分教材补充第六个特性 **可恢复性（Resiliency）**：通过冗余、备份、故障自动修复实现高可用与业务连续性。

（来源：1-云计算概念-2026.pdf 第27页）

### 3. 云计算的部署模型

- **公有云**：由第三方云提供者拥有、可公共访问。
- **私有云**：由一家组织单独拥有，用云计算技术访问内部 IT 资源。
- **社区云**：类似公有云，但访问限定为特定云用户社区。
- **混合云**：由两种或更多不同部署模型组成。

扩展部署模式：边缘云、分布式云、专属云。

（来源：1-云计算概念-2026.pdf 第28页）

### 4. 云计算的服务模型

- **IaaS（基础设施即服务）**：以**虚拟机**方式提供计算/存储/网络能力，类似"租用独立计算机"，用户自行解决多机协同。优势：动态申请释放、按量计费、资源利用率高。举例 Amazon EC2/S3（用户管系统/数据库/应用，云厂商管服务器/硬件/网络）。
- **PaaS（平台即服务）**：提供应用的**开发和运行环境**（API + 运行平台 + 封装的逻辑资源）。面向开发者，平台负责扩展与容错，用户自主权降低、需按给定编程模型开发。举例 Google App Engine、Azure。
- **SaaS（软件即服务）**：通过 **Web 浏览器/客户端**访问云上应用。举例 Salesforce CRM（用户只用，云厂商管全部）。

新型服务模式：**CaaS**（容器即服务，介于 IaaS 与 PaaS）、**FaaS**（函数即服务，事件驱动无服务器）、**DBaaS**（数据库即服务）、**AIaaS**（AI 即服务）。

（来源：1-云计算概念-2026.pdf 第10页、第29-33页）

### 5. 云计算的三元认知论

从三个视角综合认识云计算：

- **一种商业模式**：相比传统互联网服务，额外提供平台和基础设施服务；**云平台**是其具体体现。
- **一种计算范式**：
  - **云体逻辑结构**：物理结构是**云数据中心**（计算+存储+通信）。
  - **云栈逻辑结构**：物理结构是管理系统结构（IaaS+PaaS+SaaS）。
- **一种实现方式**：数据中心 + 云平台管理系统；核心是**软件定义数据中心（SDDC）**（软件定义计算/存储/网络/安全）。

（来源：1-云计算概念-2026.pdf 第36-37页）

### 6. 云计算的开源方法论

开源不仅是开放源代码的产品，更是**一种方法论、一种构造大规模复杂软件的协作方式**。

- **开源软件定义**：版权持有人为任何人和任何目的提供学习、修改和分发权力并公布源代码；许可证需满足可销售/赠予、须含源代码、允许修改和派生作品。
- **辨析**：开源不一定自由、不一定免费；自由不一定免费；免费不一定开源/自由。
- **价值意义**：促进国家信息技术创新、软件自主可控、教育科研与产业信息化；厂商降低成本提质量；用户定制降风险。
- **开源价值观**：奉献、感恩、开放、勇敢、追求进步、公平。
- **案例**：国产开源操作系统 **openEuler**。

（来源：1-云计算概念-2026.pdf 第38-40页）

## 二、云计算架构

### 1. 微服务架构

微服务架构是在 **SOA**（面向服务的体系结构）思想上，对系统业务做**彻底的组件化、服务化**：把单个业务系统拆分成多个可独立开发、独立运行的小应用，小应用之间通过服务交互和集成。

- **与 SOA 的区别**：SOA 服务面向**用户**，微服务面向**业务（开发者）**；微服务把 SOA 思想推向极致，做"彻底"的服务化拆分。
- **四大核心特征**：①通过服务实现组件化（各服务解耦、独立部署）；②按业务能力划分服务和团队；③去中心化（尤其是**数据去中心化**，每个服务管理自己的数据）；④基础设施自动化（DevOps）。

（来源：2-云计算架构-2026.pdf 第12页）

### 2. 云计算的逻辑架构

从两个正交视角刻画：**云栈（纵向）** 与 **云体（横向）**。

- **纵向——逻辑云栈**：借鉴 OSI 分层思想，组织为多个叠加层次，最下层为物理硬件，越往上易用性越高。经典**三层**：
  - **IaaS 层**：含硬件设施 + 虚拟化（虚拟化把不统一的硬件变成"标准件"）。
  - **PaaS 层**：在虚拟化资源上构建应用运行环境，提供计算环境、云存储库、通信与调度机制。
  - **SaaS 层**：基于网络远程访问的商用软件，集中式管理，"单实例多租户"，按用量计费。
  - 对应的**云计算技术体系结构**（刘鹏《云计算》参考）自下而上：物理资源层→资源池层→管理中间件层→SOA 构建层，其中**管理中间件层和资源池层最关键**。
- **横向——逻辑云体**：类比操作系统横切面（运行时环境 + 应用）。云运行时环境含计算资源、持久存储、通信，底层依托虚拟化、分布式存储与物理网络。
- **物理云体——云数据中心**：从 60 年代主机机房演进到互联网时代 IDC。传统数据中心存在机器多、利用率低、迁移难、存储增长快等问题，解决方向是**软件定义数据中心**（软件定义计算/存储/网络）。

（来源：2-云计算架构-2026.pdf 第20-33页）

### 3. 云栈和云体分别是什么？

- **云栈（又称云平台）**：**在云上建造的运行环境**，支持应用的发布、运行、监控、调度、伸缩，并提供访问控制、权限管理等辅助服务。是"软件层面的运行平台"，从**纵向**看架构（分层叠加）。
- **云体**：**云计算的物质基础**，是使用的资源集合与软硬件环境（网络、服务器、存储器、交换机等，广义还含电力、空调、机架等）。**普遍认识：云体就是数据中心**。从**横向**看架构。
- **两者与云计算的关系**：云计算是**利用云体和云平台所进行的计算或处理**，只要符合"按量计费、资源可伸缩"就是云计算。

（来源：2-云计算架构-2026.pdf 第20页）

## 三、分布式计算与存储

### 1. 分布式计算是什么？

相对于"集中式计算"，让**多台通过网络互联、各自具有计算能力的计算机协作共同完成一个任务**。优势：稀有资源共享、平衡计算负载、把程序放在最适合的机器上运行。

- **分布式系统**：建立在网络之上的软件系统，具有高度**内聚性**和**透明性**（一组独立计算机对用户呈现为统一整体）。
- **工作思想**：把大问题**拆分成小块**分配到不同节点处理，再**合并结果**；带来可用性/容错、可扩展、资源共享、更快速度等好处。
- **核心难点**：计算任务划分 + 多节点通信。

（来源：4-分布式计算-2026.pdf 第3-6页）

### 2. CAP 理论

一个分布式系统**最多只能同时满足三项中的两项**：

- **一致性（C）**：所有节点在同一时间数据完全一致。
- **可用性（A）**：服务一直可用且正常响应时间内返回。
- **分区容错性（P）**：遇到节点或网络分区故障时仍能正常对外服务。

取舍：**CA**（放弃分区容错，但分区始终存在）、**CP**（部分节点不可用）、**AP**（全局数据不一致但高可用）。互联网服务中节点/网络故障是常态，普遍采取 **AP** 策略，只保证**最终一致性**。

延伸 **BASE 理论**：Basically Available（基本可用）+ Soft State（软状态）+ Eventual Consistency（最终一致性）。达成一致需**共识算法**，典型有 **Paxos** 和 **Raft**（Raft 用强领导者机制降低实现难度）。

（来源：4-分布式计算-2026.pdf 第7-10页、第16-17页）

### 3. 一致性 HASH 算法

- **要解决的问题**：普通哈希 `Index = Hash(Key) mod N` 与服务器数 N 强相关，增删服务器时几乎所有 Key 都要重新迁移，代价极大。
- **核心思想**：把**服务器和资源(Key)都做 Hash**，映射到同一散列空间（环），Hash 与 Cache 数量无关；Key 沿环顺时针找到的第一个节点即归属节点。
- **四大性质**：**单调性**（新增/删除节点只影响相邻一小段 Key）、**平衡性**（引入**虚拟节点**避免数据倾斜，实现负载均衡）、分散性/负载、平滑性。
- **应用**：分布式键值系统（如缓存）；DHT 实现有 Chord、Pastry、Kademlia；Cassandra 冗余即用一致性哈希。

（来源：4-分布式计算-2026.pdf 第19-21页；5-分布式存储-2026.pdf 第3页、第38页）

### 4. Hadoop MapReduce 思想

核心思想来自 Google 论文——**"移动计算比移动数据更划算"**，把计算下发到数据所在机器就地计算。以词频统计为例三阶段：

- **Map（本地计算）**：各节点处理本机数据，解析成键值对（如 `<china,2>`）。
- **Shuffle（洗牌）**：把中间结果按 key 重新分组汇总到相应节点。
- **Reduce（归并）**：对同一 key 的所有值合并计算，得到最终结果（如 `<china,3>`）。

配套思想：**分布式存储 DFS**（多机硬盘连成一体、统一文件接口）；**冗余存储 + 冗余计算**保证可靠性（多机同时计算，选先结束者的结果）。

**局限**：只支持 Map/Reduce 两种模式、中间结果频繁写硬盘，对**迭代式算法（图算法、机器学习）**效率不高——这正是 Spark 要改进之处。

（来源：4-分布式计算-2026.pdf 第25页、第28-32页、第53页）

### 5. Spark RDD 思想

**RDD（弹性分布式数据集）** 是容错的、并行的、**只读的**逻辑数据结构，本质是**高度受限的共享内存模型**。基于内存计算比基于硬盘快约 100 倍。

- **五大特性**：分区列表、依赖列表、计算函数 compute、（可选）分区器、（可选）优先位置列表（呼应"移动计算比移动数据划算"）。
- **两类算子（延迟计算）**：**Transformation**（map/filter/reduceByKey 等，lazy，只构造 DAG）；**Action**（reduce/collect/count 等，遇到才真正触发提交 Job）。
- **依赖与 Stage 划分**：**窄依赖**（父 Partition 最多被 1 个子 Partition 使用，可完全并行）；**宽依赖**（需 Shuffle）。基于依赖构建 **DAG** 并划分 Stage。
- **弹性与容错**：内存/磁盘自动切换、基于 **Lineage（血统）** 高效容错（窄依赖只重算丢失的那个 Partition，宽依赖需重算父 RDD 所有 Partition）、Task/Stage 失败自动重试、Checkpoint/Persist。

（来源：4-分布式计算-2026.pdf 第54页、第61-72页）

### 6. Hadoop 和 Spark 生态

- **Hadoop 生态**：源于 Nutch 项目，借鉴 Google GFS/MapReduce/BigTable。**Hadoop 2.0** = HDFS（分布式存储）+ Yarn（资源管理）+ MapReduce + Common。
  - **HDFS**：master/slave、文件分块、NameNode/DataNode、副本冗余、心跳检测、ZooKeeper 选主。
  - **Yarn**：资源管理与调度（CapacityScheduler、FairScheduler），可编程。
  - **大家族**：ZooKeeper（协调）、HBase/Cassandra（分布式数据库）、Pig（脚本）、Hive（数据仓库/类 SQL）、Flume（数据传输）、Sqoop、Mahout、Ambari 等。
- **Spark 生态**：源于伯克利 AMP 实验室，是更通用的并行计算框架，五层：
  - **高层库**：Spark SQL、Spark Streaming、GraphX、MLlib。
  - **计算平台**：Spark 核心（RDD + Scheduler + Executor + Storage）。
  - **集群管理**：Standalone、Mesos、Yarn。
  - **数据存储**：HDFS、HBase、MongoDB、Cassandra（Spark 只算不存）。
  - **优势**：易用、多场景、通用、基于内存更快；生产中存储常仍由 HDFS 承担，两大生态互补。

（来源：4-分布式计算-2026.pdf 第33-58页）

### 7. 区块链概念

**定义**：一个共享的、不可篡改的账本，结合**分布式数据存储、点对点传输、共识机制、加密算法**等技术，用于记录交易与跟踪资产。

- **核心概念**：**区块**（含交易数据+时间戳+哈希）、**链**（每个区块含前一区块哈希）、**去中心化**、**共识机制**（PoW 工作量证明"挖矿"找 Nonce、PoS 权益证明）、**分布式账本**、**不可篡改性**（改数据会导致哈希不匹配被检测）、透明性、可编程性（**智能合约**）。
- **与传统数据库区别**：额外包含用加密技术和共识算法**验证并保护数据完整性**的机制。
- **缺点**：存储、计算开销大，不利于环保。
- **工作过程**：创建交易→验证→创建区块→挖矿→添加到链末端→完成并循环。**案例**：比特币。

（来源：5-分布式存储-2026.pdf 第7-13页）

## 四、虚拟化技术

> 虚拟化本质：添加一个"虚拟化层"，把物理资源映射为虚拟资源，实现软硬件解耦、多用户共享。（来源：6-虚拟化技术-2026.pdf 第3页）

### 1. 第一类（Type 1）与第二类（Type 2）硬件虚拟化

硬件级虚拟化的核心是 **Hypervisor（VMM，虚拟机监视器）**。Popek & Goldberg 三大要求：**同质、高效、资源受控**。

- **Type 1（裸机型 / Bare-metal）**：Hypervisor **直接运行在物理硬件**上，无宿主机 OS。结构：硬件→Hypervisor→多个 Guest VM。性能高、隔离强，面向服务器（如 VMware vSphere）。
- **Type 2（寄居型 / Hosted）**：先有**宿主机 OS**，Hypervisor 作为应用寄居其上。结构：硬件→主机 OS→Hypervisor→多个 Guest VM。部署灵活、性能略低，面向个人终端（如 VirtualBox）。

硬件级虚拟化五大优势：封装性、多实例、隔离、硬件无关性、特权功能。

（来源：6-虚拟化技术-2026.pdf 第7-8页、第11页）

### 2. 完全虚拟化 vs. 硬件辅助虚拟化 vs. 类虚拟化

| 维度 | 软件完全虚拟化 | 硬件辅助虚拟化 | 改 OS 的类虚拟化（半虚拟化） |
|---|---|---|---|
| 客户机 OS 是否修改 | 不需要，无感知 | 不需要，无感知 | **需修改内核**，客户机能感知 |
| 关键机制 | 解释执行/扫描修补/二进制翻译 | 根/非根模式 + VMCS | 超级调用 Hypercall + 特殊指令过渡模块 |
| 内存虚拟化 | 影子页表 | 扩展页表 EPT（硬件两次转换） | 直接用机器地址更新页表映射 |
| I/O 虚拟化 | VMM 拦截 + 设备模型模拟 | 硬件辅助 | 通过 VMM 接口直接与物理设备交互 |
| 性能开销 | 最大 | 小 | 小 |
| 通用性 | 最好 | 好 | 受限（需能改内核） |

- **软件完全虚拟化**：一切由 VMM 掌控，客户机无需修改，但 VMM 模拟/翻译开销最大。
- **硬件辅助虚拟化**：硬件加入虚拟化支持（Intel VT/AMD-V），引入根/非根模式与 VMCS，效率高。
- **类虚拟化（半虚拟化）**：修改客户机 OS 内核，用**超级调用**替换敏感指令，性能好但通用性受限（Windows 无法改内核）。

（来源：6-虚拟化技术-2026.pdf 第13-20页）

### 3. 操作系统级虚拟化

可看作"寄居虚拟化"的一种，但**没有 Hypervisor/VMM**，在同一操作系统内核内运行多个虚拟机（**容器**），虚拟机共享宿主机内核。

- **优点**：启动/停止开销最小、资源需求最小、可扩展性强。
- **缺点**：同一内核的虚拟机**必须使用相同的客户操作系统**，资源隔离性较差。
- **虚拟机 vs 容器**：VM 有完整 Guest OS、约 20s 启动、高成本低性能；容器只含二进制+库、共享内核、约 0.5s 启动、低成本高性能。容器镜像**不含内核**。
- **依赖机制**：cgroups（资源管理）+ namespace（隔离控制），LXC 基于此，Docker 建于其上。
- **三方案性能对比**：性能 LXC>>KVM>>XEN；隔离性 XEN>>KVM>>LXC；内存利用率 LXC>>KVM>>XEN。

（来源：6-虚拟化技术-2026.pdf 第21-24页、第32页）

### 4. VMware、Xen、KVM

- **VMware**：以完全虚拟化/硬件辅助为主；vSphere（裸机型 Type 1）、Workstation（寄居型 Type 2）。
- **Xen**：剑桥大学开源 VMM，**半虚拟化（改 OS 的类虚拟化）** 的代表，需显式修改 OS；支持不停机**实时迁移**（约 60-300s 短暂暂停）；分半虚拟化和完全虚拟化（**Windows 必须用完全虚拟化**）。
- **KVM**：本质是 **Linux 内核模块 kvm.ko**，依托硬件辅助虚拟化，让 Linux 内核直接成为 VMM，满足资源控制、等价性、效率性三条件。

（来源：6-虚拟化技术-2026.pdf 第27-31页）

## 五、容器技术

### 1. 虚拟机 vs. 容器

核心区别在**虚拟化层级**：VM 是**硬件级虚拟化**（依赖 Hypervisor，每个 VM 一套完整 OS，强隔离）；容器是**操作系统级虚拟化**（共享宿主机内核，进程级隔离）。

| 特性 | 虚拟机 | 容器 |
|---|---|---|
| 虚拟化层级 | 硬件级（Hypervisor） | 操作系统级（共享内核） |
| 隔离性 | 强隔离 | 进程级隔离 |
| 启动速度 | 分钟级 | 秒级 |
| 资源占用 | 高 | 低 |
| 镜像大小 | GB 级 | MB 级 |

容器优势：轻量、迁移部署方便、快速启动、资源占用少、硬件兼容性高。

（来源：7-容器技术-2026.pdf 第3-6页）

### 2. Namespace、Cgroup

容器隔离靠 Linux 内核的两大机制：

- **Cgroup（控制组）——限制资源用量**：限制、记录、隔离进程组使用的 CPU、内存、I/O 等物理资源。四大组件：任务、控制组、层级、子系统。
- **Namespace（命名空间）——隔离资源视图**：不同 namespace 中的程序享有独立系统资源。六种类型：**PID、User、Mount、IPC、UTS、Network**。

一句话记忆：**Namespace 管"看得见什么"，Cgroup 管"能用多少"**。

（来源：7-容器技术-2026.pdf 第7-10页）

### 3. Docker，Docker 镜像

- **Docker**：容器引擎，核心组件为 Docker Daemon（后台服务）、Docker Client（命令行）、Registry（镜像仓库）。核心技术：基于 namespace/cgroup 的隔离 + 基于**写时复制**的镜像技术。
- **Docker 镜像**：**只读的容器模板**，包含运行应用所需的文件系统、库、配置和元数据，是容器的静态快照。通过 **Dockerfile** 或 `docker commit` 构建。三大特点：**不可修改性、分层存储、版本控制（Tag）**。
- **Dockerfile 优于 commit**：可重复性、透明性、更优体积、可维护性和安全性更好。

（来源：7-容器技术-2026.pdf 第14-19页）

### 4. Docker 镜像的分层存储、写时复制机制

- **分层存储**：**base 镜像**（from scratch，直接基于宿主机内核和 bootfs）+ **扩展镜像**（FROM 逐步构建，每步形成一层 Layer）。分层可**复用层**，减少存储、加快拉取。
- **写时复制（COW）**：底层机制是 COW + UnionFS（如 OverlayFS）。所有层只读，修改文件时先从下层**复制到上层可写层再改**。
- **加速构建**：缓存构建（复用未变化的层）、多阶段构建（多个 FROM，只保留必要文件、减小体积）。
- **容器与镜像关系**：每个容器基于镜像运行，拥有独立的**容器层（可写层）**；容器层+镜像可提交为新镜像。二者是同一对象的动态与静态，底层都是 UnionFS。

（来源：7-容器技术-2026.pdf 第20-24页）

### 5. K8S（Kubernetes）

开源的分布式系统框架，用于自动部署、扩缩和管理容器化应用，源自 Google 生产经验。

- **核心思想**：**声明式**——不是面向过程，而是一组独立可组合的控制过程，**持续把当前状态驱动到预期状态**，中间过程对用户透明。
- **Pod**：最小可部署计算单元，含一个或多个紧密耦合容器，共同调度，共享 Namespace/cgroup/卷/网络。
- **工作负载**：Deployment（无状态应用）、DaemonSet（每节点运行）、StatefulSet（有状态应用）。
- **Service 四种类型**：ClusterIP（集群内部，默认）、NodePort（节点 IP+静态端口，外部可访问）、LoadBalancer（云平台负载均衡器）、ExternalName（外部服务暴露到集群内）。
- **持久化存储**：PV（存储资源对象）+ PVC（对 PV 的请求）；流程：管理员建 PV→用户建 PVC 绑定→Pod 声明使用 PVC。
- **调度器（Scheduler）**：调度最小单位是 Pod；**调度 = 调度决策 + 绑定**，**调度决策 = 预选（predicates 过滤）+ 优选（priorities 打分）**，绑定记录写入 **etcd**。调度器框架支持插件化扩展。
- **亲和性调度**：Node 亲和性、Pod 亲和性；硬亲和（必须符合）、软亲和（按权重）。配置文件用 JSON/YAML。

（来源：7-容器技术-2026.pdf 第36-62页）

## 六、云计算网络与云数据中心

### 1. 软件定义网络（SDN）的概念

核心思想：**控制转发分离 + 可编程性**。传统网络设备把"数据转发（数据平面）"和"路由控制（控制平面）"耦合在一起，难管理、难革新。SDN 把两者拆开：

- **控制转发分离**：控制逻辑抽出集中到**集中式控制器（Controller）**，设备只保留数据转发。
- **逻辑上集中控制**：Controller 通过标准化接口统一管理配置设备，"像对整个网络整体编程"。
- **可编程性**：控制平面与转发平面之间提供可编程接口。

> 注意：SDN 的集中控制思想恰是对早期互联网**分散控制思想的颠覆**。

（来源：8-云计算网络-2026.pdf 第40页、第42-43页）

### 2. OpenFlow、SDN、Overlay、P4、软硬件融合可编程网络的发展历程

按时间轴记忆：

1. **2006 SANE**（Martin Casado）：集中控制思想的萌芽，解决网络安全。
2. **2007 Ethane**：SDN 雏形，集中式 Controller 定义基于网络流的安全策略。
3. **2008-2009 OpenFlow / SDN**：Nick McKeown 等发表 OpenFlow 论文，Controller 通过 **OpenFlow 协议**控制 Switch 的**流表**；2009 正式提出 SDN 概念。
4. **2010-2012 Google B4**：Google 骨干网大规模用 OpenFlow，是**首个跳出数据中心、在骨干网成功的 SDN 案例**。
5. **Overlay（广义 SDN）**：面向虚拟机，在物理网络上**叠加虚拟网络**，用**隧道技术**+ OVS 虚拟交换机 + VLAN 标签，实现 VM 灵活配置、迁移与隔离。
6. **2014 P4 + Tofino**：OpenFlow 只是软件层、功能受制于硬件；**P4**（协议无关、目标无关、可重配置的 DSL）+ Barefoot **Tofino** 可编程芯片实现**数据平面可编程**，把网络功能设计交给开发者。
7. **软硬件融合的完全可编程网络**（McKeown 定义 SDN 三阶段）：①2010-2020 软件层（OpenFlow 控制转发分离）；②2015-2025 硬件层（P4 数据面可编程）；③2020-2030 软硬件融合（网卡/交换机/协议栈均可编程，整个网络成为可编程平台）。

**主线**：SANE/Ethane→OpenFlow/SDN→Google B4→Overlay→P4+Tofino→软硬件融合完全可编程网络。

（来源：8-云计算网络-2026.pdf 第40-53页）

### 3. 数据中心节能、容灾

**（一）绿色节能技术**（背景：数据中心高能耗；思路"高能效+新能源"）五大类：

1. **配电系统节能**：高压直流配电、市电直供、微软电网互动式 UPS 电池（储能效率达 90%）。
2. **空调系统节能**：用 **PUE**（Power Usage Effectiveness，基准 2，越接近 1 越好）衡量；高温回风、精确制冷、冷热通道密封、液浸冷却、自然冷（新风/水）。
3. **集装箱数据中心**：高密度、模块化、按需快速部署、Free Cooling。
4. **管理系统节能**：动态功率管理 DPM（如 **DVFS** 动态调压调频）、静态功率管理 SPM、虚拟机迁移节能。
5. **新能源应用**：太阳能、风能、生物质能等。
   - 案例 PUE：雅虎"鸡窝"1.08、Facebook 1.15、谷歌比利时 1.16、微软都柏林 1.25；微软海底数据中心；华为贵州溶洞数据中心。

**（二）容灾与备份**

- **备份 vs 容灾**：备份防**数据丢失**（成本 1~2%）；容灾防**业务中断**（成本 20%~100%）。
- **两个关键指标**：**RPO**（可容忍的数据丢失量）、**RTO**（可容忍的业务停止时间）。
- **容灾两个层次**：数据级容灾（保数据，但服务会中断）、应用级容灾（不间断应用服务）。
- **标准等级**：IBM SHARE78（Tier-0~Tier-6）、国标 GB/T 20988-2007（第一~六级），逐级增强，**Tier-6 数据丢失率为零、双中心负载均衡**。
- **关键技术**：**镜像技术**（本地/远程/流镜像，远程分同步/异步）、**快照技术**（COW 写时复制、I/O 重定向）、基于 IP 的 SAN 容灾、数据库复制（如谷歌 Spanner）。

（来源：9-云数据中心-2026.pdf 第17-45页）

## 七、OpenStack

### 1. OpenStack 的定义

**开源的云计算平台**，控制整个数据中心的大型计算、存储和网络资源池，提供部署云的操作平台和工具集，可构建公有云/私有云。管理员通过 Web/命令行/API 控制配置资源，普通用户通过 Web 申请使用资源。

- 定位为**云计算系统的控制面**，三特点：**自身不提供虚拟化技术**、**调用底层技术**管理多资源池、对外提供**统一管理接口**。可类比"**云操作系统**"。
- 三大设计理念：**开放（Open）、灵活（Flexible，插件化）、可扩展（Scalable，无中心/无状态）**。

（来源：10-OpenStack-2026.pdf 第3页、第5-10页、第51页）

### 2. 核心组件及功能

- **Keystone（身份认证）**：身份认证 + 服务目录，各服务向其注册 API 端点（注册中心）；含身份/资源/认证/令牌/目录/策略等 Provider，访问需有效**令牌 Token**。
- **Nova（计算，最核心）**：虚拟机生命周期管理。子组件：**nova-api**（编排引擎，写数据库+消息队列）、**nova-conductor**（代计算节点做数据库操作，隔离数据库访问）、**nova-scheduler**（调度器，过滤+加权选最佳节点）、**nova-compute**（运行在计算节点，控制 Hypervisor 启停虚拟机）。
- **Glance（镜像）**：管理操作系统镜像；Glance API（REST 接口）+ Glance registry（元数据存数据库，镜像存后端如 Swift）。
- **Swift（对象存储）**：PB 级对象存储，扁平命名空间，REST/SOAP 访问；用**一致性 Hash 环（Ring）**映射账户/容器/对象到物理位置。
- **Cinder（块存储）**：统一接口、按需分配、持久化的卷管理（卷/卷类型/快照/备份）。
- **Neutron（网络）**：动态配置公网 IP、建私有网络；基于插件架构（API 服务器+核心插件+服务插件+Agent）；用 OVS+VLAN 隔离租户，浮动 IP/SNAT/DNAT 对外访问，DVR 分布式虚拟路由。
- **其他**：Horizon（仪表盘 GUI）、Telemetry（计量计费）、Manila（文件共享）、Heat（编排）、Magnum（容器编排）。
- **两个基础组件**：**消息队列**（服务间传消息、缓冲请求，如 RabbitMQ）、**数据库**（存构建时/运行时状态，如 MySQL）。

（来源：10-OpenStack-2026.pdf 第13页、第15页、第22-44页）

### 3. 以虚拟机创建为例的组件协作流程

组件通过 **RESTful API + 消息队列 + 数据库**三种媒介松耦合协作：

1. **身份认证（Keystone）**：用户请求先经 Keystone 认证获**令牌**，并从服务目录获取各服务端点。
2. **请求进入 nova-api**：携令牌请求到 nova-api，校验令牌→把虚拟机信息**写数据库**→通过**消息队列**驱动后续流程。
3. **调度决策（nova-scheduler）**：过滤检查各计算节点资源可用性，加权选出启动虚拟机的最佳计算节点。
4. **准备镜像（Glance）**：Glance API 查询镜像及元数据，registry 读元数据，从后端（如 Swift）取镜像。
5. **计算节点创建（nova-compute + Hypervisor + nova-conductor）**：scheduler 经 MQ 通知目标节点 nova-compute；nova-compute 经 conductor 从数据库取详细信息，再控制该节点 **Hypervisor** 真正启动虚拟机。
6. **存储与网络接入**：**Cinder** 按需分配块存储卷（需分区、建文件系统、挂载）；**Neutron** 分配端口、接入租户虚拟网络、分配浮动 IP。

**小结**：Keystone 管认证、Nova 管计算调度与创建、Glance 供镜像、Cinder 供块存储、Neutron 供网络，靠统一 API + 消息队列 + 数据库实现松耦合协作。

（来源：10-OpenStack-2026.pdf 第15-16页、第20页、第24-29页、第38页、第43页、第45页、第51页）

## 八、云计算安全

### 1. 云场景下的安全维度、典型问题和对应解决方案

- **四大安全维度**：①数据存储与计算安全；②虚拟化安全；③网络安全；④访问控制。
- **贯穿总原则——云安全责任共担**：云服务商与客户共同分担；不同服务模式责任边界不同：IaaS（商保底层与虚拟化，客户管 OS/网络/应用）、PaaS（商还保 OS/中间件/Runtime）、SaaS（商保到应用层并提供数据加密，客户负责数据安全）。
- **企业级架构示例**：移动云"三横两纵"（用户安全、云平台安全、安全合规 + 安全管理、安全运营），运营遵循"事前预防、事中管控、事后处置"闭环。

（来源：11-云计算安全-2026.pdf 第2-3页、第11页、第17页、第31页、第38-39页）

### 2. 数据存储与计算安全问题

- **问题**：数据存云端引来存储与计算阶段隐患；大规模公有云并非绝对稳定（如阿里云故障）。
- **解决方案**：多地域多可用区混合云提升可信度；数据**加密与密钥管理**（HSM 硬件密码机、根密钥保护、客户自管密钥使第三方无法解密）；**敏感数据脱敏**（静态/动态）；**数据库审计**；**数据全生命周期保护**（上云/云中/下云三阶段，境内存储、多副本备份、逻辑/物理擦除）；存储产品自身安全（EOS/云硬盘加密/文件存储）。

（来源：11-云计算安全-2026.pdf 第6页、第20页、第24页、第55-57页、第60页、第75-76页）

### 3. 虚拟化安全问题

- **问题**：虚拟化使资源灵活分配，但**虚拟机/容器逃逸**成为常见攻击；很多事故本质是"运维的锅"。自建云应及时修漏洞，用第三方云需加强其他方面弥补。
- **解决方案（多租户隔离为核心）**：**CPU 隔离**（ROOT/NON-ROOT 模式 + VMCS）、**内存隔离**（硬件辅助两次地址转换、实例释放刷 TLB）、**存储隔离**（IO 敏感指令触发 VM-Exit）、**网络隔离**（VPC + cgroup/namespace）、**镜像安全**（基础加固、深度扫描）、**安全加固**（裁剪代码降攻击面、授信执行环境）、**容器安全产品**（镜像漏洞扫描、检测逃逸、行为白名单）。

（来源：11-云计算安全-2026.pdf 第7-8页、第19页、第24页、第50-52页、第71页）

### 4. 网络安全问题

- **问题**：公有云对公网暴露带来的一系列安全问题（如个人信息被盗催生电信诈骗），部分风险本与云无关但会影响云上服务。
- **解决方案**：**SDN 网络隔离**（VPC + 网络 ACL + 安全组）、**抗 DDoS**（流量清洗）、**Web 应用防护 WAF**（防 SQL 注入/XSS/CSRF 等 OWASP 威胁）、**态势感知**（大数据发现告警）、**云下一代防火墙**、**入侵检测**、**增强漏洞扫描**。

（来源：11-云计算安全-2026.pdf 第9页、第19页、第21-22页、第67-69页、第72页、第74页）

### 5. 访问控制安全问题

- **问题**：访问控制始终是 IT 安全核心；公有云若被攻破或多租户隔离被打破，影响面广泛，需更高安全意识与实践。
- **解决方案**：两大基本原则——**责任匹配**和**最小授权**；**账号管理**（双因子认证、复杂密码、禁共享、SSO/AK）；**权限管理**（工单申请、审批、自动开通回收）；**访问控制**（重要系统设"金库指令"、实时审批、安全审计）；**身份安全产品**（身份认证、**云堡垒机**、日志审计）；**SSL 证书管理**。

（来源：11-云计算安全-2026.pdf 第10页、第17页、第23页、第25页、第43页、第56-57页、第68页、第72页）

## 九、云原生

### 1. 云原生的定义、概念

**云原生是一种构建和运行应用程序的理念和方法**，充分利用云计算模型优势，使应用在动态、弹性的云环境中最大化发挥业务价值与技术潜力。

- **三个要点**：不是单一技术而是体系集合；天生适应云环境；以应用为中心的思维范式转变。
- **六大特征**：分布式架构部署、极致弹性资源调度、全链路自动化运维、故障智能自愈、全栈可观测性、不可变基础设施。
- **通俗理解**："上云"只是搬到云服务器上跑，"云原生"是让应用从架构设计上就为云而生。

（来源：12-云原生.pdf 第3-4页）

### 2. 云原生四大核心内容及对应落地技术

思想角度四大核心内容（第8页）+ 技术角度四要素（第13页），一一对应：

| 核心内容（思想） | 对应落地技术 |
|---|---|
| **敏捷基础设施** | 基础设施即代码（IaC）/ 自动化配置 |
| **持续交付** | 持续集成 CI + 持续部署 + 持续发布 |
| **DevOps** | 集成的自动化工具链 |
| **微服务** | 服务拆分 + 容器化 + 容器编排（Kubernetes） |

- **第四要素——容器（技术底座）**：相比虚拟机更轻、更快，保持环境一致性（Docker"一次编译，到处运行"），结合 **Kubernetes** 增强扩展性和自愈能力（CNCF 核心）。
- **思想与云上特性对应**：DevOps/持续交付→敏捷性；微服务→可扩展性与故障可恢复性；敏捷基础设施→资源层支持；康威定律→组织与流程保障。

（来源：12-云原生.pdf 第8-9页、第10-13页、第17页、第19-20页）

### 3. 微服务的概念、优势、挑战

- **概念**：一种架构风格与服务形态，颗粒小、松耦合、可独立开发部署的无状态化服务（UNIX 哲学"每种服务只做一件事"，如 Netflix 由 500+ 微服务组成）。
- **为何需要（单体架构问题）**：迭代慢、木桶效应严重、资源利用不充分。**康威定律**：系统设计等同于组织的沟通结构。
- **优势**：独立部署与迭代、故障域隔离、技术栈灵活适配、弹性伸缩与团队自治。
- **挑战**：分布式系统固有复杂性（超时/重试/熔断）、服务治理复杂、跨服务一致性保障困难、接口契约管理风险。

（来源：12-云原生.pdf 第12页、第14页；12-云原生案例.pdf 第4页）

### 4. DevOps

- **定义**：一组过程、方法与系统的统称，是**开发、技术运营、质量保障三者的交集**。
- **三层内涵**：组织架构/文化理念（自上而下促进三部门协作）、自动化（无需人工参与）、产生原因（开发与运维必须紧密合作以按时交付）。
- **核心作用**：自动化软件交付和架构变更流程，使构建、测试、发布更快捷、频繁、可靠。
- **引入因素**：敏捷方法、加快交付要求、虚拟化/云基础设施普及、数据中心自动化工具普及。
- **落地实践（CI/CD 流水线七步）**：代码 Push→WebHook 触发 CI→拉依赖跑测试/扫描→构建镜像→推 Harbor 仓库→Argo CD GitOps 同步滚动更新 K8s→冒烟测试。工具：Jenkins、GitLab CI、Argo CD、Kubernetes。

（来源：12-云原生.pdf 第11页、第15-17页；12-云原生案例.pdf 第11页）

### 5. 持续交付

- **定义**：以可持续方式**安全快速地将所有类型软件变更转化为生产环境可交付产品**的软件过程控制方法，最终目标是将变更部署到生产环境。
- **三大核心环节**：**持续集成 CI**（每次提交自动触发构建与测试）、**持续交付 CD**（推送稳定版本到预发布环境）、**持续部署**（自动分发到测试环境）。
- **与 CI 关系**：CI 强调频繁整合，持续交付强调安全快速转化并部署；CI 是基础，持续交付是延伸。
- **落地形态——GitOps**：以 Git 为**单一事实来源**，声明式存储配置、Agent 持续同步集群状态；优势：可追溯可回滚、环境一致、变更安全可控、自动化。工具 **Argo CD**。

（来源：12-云原生.pdf 第10页、第18页；12-云原生案例.pdf 第12页）

### 6. 云原生案例：传统 ERP 系统转型云原生

- **背景（单体 ERP 四大问题）**：高度耦合、部署周期长、故障影响大、技术陈旧。转型核心决策：以分布式复杂性换取业务敏捷性与弹性。
- **① 微服务拆分**：三原则（单一职责、高内聚松耦合、数据自治"一服务一数据库"）；业务域分层（交易中台层、共享基础层、通用能力支撑层）；通信（RESTful 同步 + 消息中间件异步）。
- **② 容器化**：Docker"一次构建到处运行"四步（环境定义标准化→镜像不可变→Harbor 统一管理→全环境一致交付）。
- **③ 容器编排（Kubernetes）**：全生命周期自动化发布回滚、零宕机自愈、智能弹性扩缩容、服务发现与负载均衡。核心资源 Pod/Deployment/Service/ConfigMap。
- **④ 微服务治理（Service Mesh / Istio）**：Sidecar 模式把流量治理下沉到基础设施层，实现流量管理、零信任安全（mTLS）、无侵入可观测性。
- **⑤ 稳定性/可观测性/安全**：流量治理+发布策略+高可用+故障演练；三大支柱 Metrics（Prometheus+Grafana）/Logs（ELK）/Tracing（Jaeger）；**DevSecOps**（镜像扫描 Trivy、运行时 Falco、密钥 Vault、安全左移）。
- **⑥ 转型路线（三阶段）**：试点验证（3~6 月）→全面推广（6~12 月）→深化优化（1~2 年，探索 Serverless）。

（来源：12-云原生案例.pdf 第3-16页）
