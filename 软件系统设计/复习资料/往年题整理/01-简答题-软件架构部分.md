## 题1：软件架构的来源

**【2015】【2019】** Where do software architecture come from? List five possible sources.

> 出处：[2015真题第1页](../往年题/2015/1.jpg)、[Exam0-往年考试.pdf#p5](../往年题/Exam0-往年考试.pdf#page=5)

### 标准答案

软件架构的来源包括：

1. **NFRs（非功能需求）**：包括约束和质量属性
2. **ASRs（架构攸关需求）**：对体系结构产生深远影响的需求
3. **Quality Requirements（质量需求）**：在功能需求基础上需满足的特征
4. **Stakeholders（利益相关者）**：系统的各类涉众
5. **Organisations（开发组织）**：组织结构影响架构（康威定律）
6. **Technical Environments（技术环境）**：已有技术栈和平台
7. 不仅仅局限于需求，可能是**商业和技术决定的集合**

> **关联资料**：[笔记-系统架构（简）#p3](../笔记/软件系统设计-系统架构（简）.pdf#page=3) — 软件系统架构的来源；[笔记-系统架构#p11](../笔记/软件系统设计-系统架构.pdf#page=11) — 软件体系结构章节

## 题2：软件架构过程的一般活动及输入输出

**【2015】【2017】** Briefly describe the general activities in a software architecture process, and the major inputs and outputs at each activity.

> 出处：[2015真题第1页](../往年题/2015/1.jpg)、[押题汇总#p1](../往年题/2015、2017、2018、2019押题、2019.pdf#page=1)、[Exam0-往年考试.pdf#p3](../往年题/Exam0-往年考试.pdf#page=3)

### 标准答案

#### 短答版（推荐背诵）

| 步骤 | 输入 | 输出 |
|------|------|------|
| 1. 识别ASRs | 无 | 优化的质量属性场景 |
| 2. 架构设计 | 优化的质量属性场景、需求和约束、模式和决策 | 一组候选视图的草图（模式决定） |
| 3. 架构文档化 | 一组模式决定的草图 | View & Beyond |
| 4. 架构评估 | View & Beyond、优化的质量属性场景 | View & Beyond（评估后） |

#### 长答版

1. **创建商业案例**：输入-问题域，输出-商业案例
2. **了解用户需求**：输入-用户的模糊需求，输出-架构攸关的需求
3. **创建或选择体系结构**：输入-策略、模式和备选场景，输出-被选中的策略、模式和场景
4. **沟通体系结构**：输入-架构设计文档，输出-（文档化的架构）
5. **分析和评估体系结构**：输入-架构设计文档，输出-（评估报告）
6. **实现体系结构**：输入-架构设计文档，输出-架构设计的具体实现
7. **保证体系结构的一致性**：输入-架构设计的具体实现，输出-保持一致的架构设计具体实现

> **关联资料**：[笔记-系统架构#p5](../笔记/软件系统设计-系统架构.pdf#page=5) — 软件体系结构概念/活动；[笔记-系统架构（简）#p5](../笔记/软件系统设计-系统架构（简）.pdf#page=5) — 软件体系结构活动

## 题3：为什么软件架构需要用不同视图文档化？列出4种视图

**【2015】【2017】【2019】高频** Why should a software architecture be documented using different views? Give the names and purposes of 4 example views.

> 出处：[2015真题第2页](../往年题/2015/2.jpg)、[Exam0-往年考试.pdf#p2](../往年题/Exam0-往年考试.pdf#page=2)

### 标准答案

#### 为什么需要不同视图：

1. 不同视图支持不同的目标和用户，突出不同的系统元素和关系
2. 不同视图将不同质量属性暴露出不同的程度

#### 4种视图：

1. **模块视图 Module View**：提供一组连贯职责的实现单元
2. **组件和连接器视图 C&C View**：显示具有某些运行时存在的元素
3. **分配视图 Allocation View**：描述了软件单元到软件开发或执行环境元素的映射
4. **质量视图 Quality Views**：安全视图、性能视图、可靠性视图、沟通视图、异常（错误处理）视图

#### 组合视图：将上述视图进行组合

> **关联资料**：[笔记-系统架构#p49](../笔记/软件系统设计-系统架构.pdf#page=49) — 架构文档化/为什么记录；[笔记-系统架构（简）#p4](../笔记/软件系统设计-系统架构（简）.pdf#page=4) — 体系结构视图

## 题4：描述4+1视图

**【2017】【2019】** Describe 4+1 view（需掌握绘图）

> 出处：[Exam0-往年考试.pdf#p2](../往年题/Exam0-往年考试.pdf#page=2)、[押题汇总#p2](../往年题/2015、2017、2018、2019押题、2019.pdf#page=2)

### 标准答案

1. **逻辑视图（Logical View）**：描述了对架构而言重要的元素和他们之间的关系（功能需求）
2. **过程视图（Process View）**：描述了元素之间的并发和交互
3. **物理视图（Physical/Deployment View）**：描述了主要过程和组件是如何被映射到硬件上的
4. **发展视图（Development/Implementation View）**：描述了软件组件的内部组织联系（如使用配置管理工具存储）
5. **用例场景（Use Case）**：捕获架构需求，与一个或多个特定视图相关

#### 4+1视图结构（需画图）：
```
         逻辑视图          发展视图
              \            /
               用例场景
              /            \
         过程视图          物理视图
```

对应关系：
- 逻辑视图 → End User/Functionality → Class, subsystems
- 发展视图 → Programmer/Software Management → component
- 过程视图 → System Integrators/Performance → statechart
- 物理视图 → System Engineering/Topology → deployment

> **关联资料**：[笔记-系统架构（简）#p4](../笔记/软件系统设计-系统架构（简）.pdf#page=4) — 4+1视图（含图）

## 题7：ATAM中的Stakeholder及其职责

**【2019】** 描述在ATAM的每一个过程中有哪些stakeholder和他们的职责

> 出处：[押题汇总#p2](../往年题/2015、2017、2018、2019押题、2019.pdf#page=2)、[Exam0-往年考试.pdf#p5](../往年题/Exam0-往年考试.pdf#page=5)

### 标准答案

**阶段-0：准备和建立团队**
- 参与者：评估团队领导和关键项目决策者
- 职责：根据架构设计文档生成评估计划

**阶段-1：评估-1**
- 参与者：评估团队和项目决策者
- 职责：
  - 第一步：评估负责人介绍ATAM方法
  - 第二步：项目经理或客户从业务角度介绍业务驱动因素
  - 第三步：首席架构师介绍体系结构
  - 第四步：评估团队确定架构方法
  - 第五步：评估团队和项目决策者生成质量属性效用树(Utility Tree)
  - 第六步：评估团队分析架构方法

**阶段-2：评估-2**
- 参与者：评估团队、项目决策者和项目涉众
- 职责：
  - 第七步：涉众头脑风暴并确定场景优先级
  - 第八步：评估团队分析架构方法（类似第六步）
  - 第九步：评估团队展示评估结果，并呈递涉众

**阶段-3：后续**
- 参与者：评估团队、主要涉众
- 职责：评估团队制作最终评估报告，发给主要涉众审核通过后，将报告呈递给委托评估的人

> **关联资料**：[笔记-系统架构#p60](../笔记/软件系统设计-系统架构.pdf#page=60) — ATAM Phase 0-3参与者与职责

## 题8：什么是ASR？列出4种提取和识别ASR的来源和方法

**【2017】【2019】** What are ASR? List four sources and methods for extracting and identifying ASRs.

> 出处：[Exam0-往年考试.pdf#p6](../往年题/Exam0-往年考试.pdf#page=6)、[押题汇总#p1](../往年题/2015、2017、2018、2019押题、2019.pdf#page=1)

### 标准答案

**ASR定义**：架构攸关需求（Architecturally Significant Requirements），是对体系结构产生深远影响的需求，是软件需求的一部分。

**四种来源和方法**：

1. **从需求文档中收集ASR**：MoSCoW方法和用户故事
2. **通过采访涉众来收集ASR**：质量属性工作坊（QAW）
3. **通过了解业务目标来收集ASR**：业务目标驱动
4. **通过质量属性实体树(Utility Tree)来管理ASR**：通过方案量化描述需求后，逐渐对质量属性进行分解细化，直到包含量化指标为止

> **关联资料**：[笔记-系统架构#p28](../笔记/软件系统设计-系统架构.pdf#page=28) — ASR章节；[旧课件-质量属性#p3](../../../旧课件/2025_UG_SysArch2-3_quality%20attributes.pdf#page=3) — ASR定义与4种收集方法

## 题9：描述ADD过程

**【2018】【2021】【2025】** 描述ADD过程

> 出处：[Exam0-往年考试.pdf#p9](../往年题/Exam0-往年考试.pdf#page=9)、[押题汇总#p2](../往年题/2015、2017、2018、2019押题、2019.pdf#page=2)（2018题8）、[2025期末](../往年题/软统25期末-不完全准确.jpeg)

### 标准答案

ADD（Attribute Driven Design）过程步骤：

1. **确定有足够的需求信息**
2. **选择要分解的系统要素**
3. **确定所选元素的ASR**
4. **选择符合ASR的设计**：
   1. 找出设计问题
   2. 列出子关注点替代模式/决策
   3. 从清单中选择模式/决策
   4. 确定模式/决策与ASR之间的关系
   5. 记录初步的架构视图
   6. 评估并解决不一致的问题
5. **实例化架构元素并分配职责**
6. **实例化元素定义接口**
7. **验证和完善需求**
8. **重复进行2-7步直到满足所有的ASR**

> **关联资料**：[笔记-系统架构#p46](../笔记/软件系统设计-系统架构.pdf#page=46) — ADD属性驱动设计（Steps 1-8详解）

## 题10：Software requirements, Quality attributes, ASRs的区别和联系

**【2018】【2022】** 

> 出处：[押题汇总#p2](../往年题/2015、2017、2018、2019押题、2019.pdf#page=2)（2018题2）、[2022试卷#p1](../往年题/软统2022试卷.pdf#page=1)（题6）、[Exam0-往年考试.pdf#p9](../往年题/Exam0-往年考试.pdf#page=9)

### 标准答案

1. **软件需求**包括功能性需求和非功能性需求（又称质量需求）
2. **质量属性**是由软件的业务目标所决定，在功能性需求的基础上提供的整个系统的合乎需求的特性，是非功能需求的一种反应
3. **ASRs**架构攸关需求是对于体系结构有着深远影响的需求，肯定是软件需求的一部分

**关系**：软件需求 ⊃ 质量属性 ⊃ ASRs（层层递进，ASR是最核心的影响架构的需求子集）

> **关联资料**：[笔记-系统架构#p14](../笔记/软件系统设计-系统架构.pdf#page=14) — 需求/质量属性章节

## 题11：软件架构文档包应包含什么内容

**【2017】【2019】** What should be included in a typical software architecture documentation package?

> 出处：[Exam0-往年考试.pdf#p6](../往年题/Exam0-往年考试.pdf#page=6)

### 标准答案

包含 **View** 和 **Beyond** 两部分：

#### Beyond部分：
1. **文档路线图**：包含了范围和总结、简单摘要等
2. **视图的文档组织方式**：描述了本文档中视图是如何组织的
3. **系统概述**：从整体上描述了当前架构的简要说明、业务目标（驱动因素）等
4. **视图之间的映射关系**：描述了不同视图之间的映射关系
5. **系统原理**：从整体上描述了当前架构的设计原理
6. **目录**：索引、词汇表、首字母缩略词表

#### View部分：
1. Styles and Views（体系结构风格和视图）
2. Structural Views：Module views、C&C views、Allocation views
3. Quality Views

#### 每一个View的内容：
1. **主要介绍**：显示视图的元素和关系，以及图例
2. **元素介绍**：详细介绍第一部分中描述的元素、元素属性、关系属性和元素接口和行为
3. **上下文图**：描述系统如何与环境相关
4. **可变性指南**：告知视图中可能出现的变化
5. **基本原理**：解释设计如何映射在视图中，以及其合理性

> **关联资料**：[笔记-系统架构#p51](../笔记/软件系统设计-系统架构.pdf#page=51) — View部分详解；[笔记-系统架构#p57](../笔记/软件系统设计-系统架构.pdf#page=57) — Beyond部分详解

1. **抽象**：使用抽象让设计师关注本身结构而不关心实现，比如将系统抽象为组件和连接件或抽象为模块
2. **分解**：针对某一个系统关注点分解后处理，比如将整个系统分解或将某个模块分解
3. **分而治之**：将每个模块分别处理
4. **生成与测试**：将一个特定的设计看作是一个假设；根据测试路径生成测试用例
5. **迭代与细化**：使用迭代的方法，ADD方法多次迭代直到满足所有ASR
6. **复用元素**：重用在设计过程中出现了可以复用的元素，重用现有架构

## 题15：Architecture, Structure和Design的区别

**【2019】**

> 出处：[Exam0-往年考试.pdf#p9](../往年题/Exam0-往年考试.pdf#page=9)

### 标准答案

1. Design 包含 Architecture，Architecture 包含 Structure
2. 结构是静态的、逻辑的，是关于系统如何构成的
3. 体系结构除包含架构，还会包含组件之间的相关的关系结构，并定义一些动态的行为
4. 体系结构是关于软件设计的，所有体系结构都是设计，但不是所有的设计都是体系结构，体系结构是软件设计的一个部分

## 题16：为什么设计决定对架构很重要？

**【2021】** 说出你对"软件架构=设计（如，组件-连接器）+设计决定"的理解

> 出处：[2021 痛苦回忆.pdf#p1](../往年题/2021%20痛苦回忆.pdf#page=1)

### 标准答案

软件架构不仅是组件和连接器的结构，还包含设计决定。设计决定记录了架构师在设计过程中做出的选择及其理由（rationale），包括：
- 为什么选择某个模式而非另一个
- 什么约束导致了这个选择
- 哪些备选方案被排除以及原因

没有设计决定，架构仅是静态结构图；有了设计决定，架构才是可理解、可评估、可演进的完整知识体。

> **关联资料**：[笔记-系统架构#p7](../笔记/软件系统设计-系统架构.pdf#page=7) — 软件体系结构概念

## 题17：什么需求影响架构？怎么得到？

**【2025】**

> 出处：[2025期末](../往年题/软统25期末-不完全准确.jpeg)（题1）

### 标准答案

同题8（ASR）+ 题12。影响架构的需求是**ASR（架构攸关需求）**。

获取方式：
1. 从需求文档中收集（MoSCoW方法、用户故事）
2. 通过涉众访谈（QAW质量属性工作坊）
3. 通过业务目标分析
4. 通过Utility Tree（效用树）进行量化管理
