## 设计题1：策略模式 - 飞行模拟软件

**【2018】** 设计一个飞行模拟软件，要求能模拟多种飞机的特性。为了在将来支持更多飞机种类，要求使用策略模式。画出架构图和类图。

> 出处：[押题汇总#p2](../往年题/2015、2017、2018、2019押题、2019.pdf#page=2)（2018题11）

### 参考答案（采用模板 4.4）

#### 1. 使用的模式

使用 **Strategy（策略模式）**。

#### 2. 模式意图

把不同飞行算法封装成可替换的策略对象，使飞机对象可以在不修改自身代码的情况下选择或更换飞行方式。

#### 3. 角色映射

| 策略模式角色 | 题目中的类 |
|---|---|
| Context | `Aircraft` |
| Strategy | `FlyBehavior` |
| ConcreteStrategy | `SubSonicFly`、`SuperSonicFly`、`HelicopterFly` |
| Client | 创建飞机并设置飞行策略的程序 |

#### 4. 类图/文字结构

```text
Aircraft o---- FlyBehavior
                    ^
                    |
        +-----------+-------------+
        |           |             |
 SubSonicFly  SuperSonicFly  HelicopterFly

Aircraft
  ^
  +-- Fighter
  +-- Bomber
  +-- Chopper
```

`Aircraft` 组合一个 `FlyBehavior`，`performFly()` 将飞行行为委托给策略对象。

#### 5. 关键代码

```java
public interface FlyBehavior {
    void fly();
}

public final class SuperSonicFly implements FlyBehavior {
    @Override
    public void fly() {
        System.out.println("fly at supersonic speed");
    }
}

public abstract class Aircraft {
    private FlyBehavior flyBehavior;

    protected Aircraft(FlyBehavior flyBehavior) {
        this.flyBehavior = flyBehavior;
    }

    public void performFly() {
        flyBehavior.fly();
    }

    public void setFlyBehavior(FlyBehavior flyBehavior) {
        this.flyBehavior = flyBehavior;
    }
}
```

#### 6. 体现的设计原则

- **OCP**：增加新飞行方式只需增加新的 `FlyBehavior` 实现。
- **DIP**：`Aircraft` 依赖 `FlyBehavior` 抽象，不依赖具体算法。
- **SRP**：飞机负责飞机属性，策略类负责飞行算法。
- **CRP**：通过组合策略获得变化行为，而不是为每种飞行方式建立大量子类。

#### 7. 优缺点与适用场景

优点：消除飞行算法条件分支，算法可独立测试并可在运行时替换。  
缺点：类数量增加，客户端必须知道各策略差异。  
适用：系统存在多种可互换算法，且算法经常扩展或切换。

> **关联资料**：[课件-策略模式](../../课件/02策略模式.pdf)；[pmx-策略模式](../../旧课件/pmx/02策略模式.pdf)

## 设计题2：策略模式 - 买票系统打折

**【2019】** 一个买票系统，不同角色有不同的打折方案，用策略模式设计，画图，并说明策略模式的使用场景。

> 出处：[押题汇总#p1](../往年题/2015、2017、2018、2019押题、2019.pdf#page=1)

### 参考答案（采用模板 4.4）

#### 1. 使用的模式

使用 **Strategy（策略模式）**。

#### 2. 模式意图

把学生、军人、VIP 等不同计价算法封装成独立策略，让售票上下文在运行时选择折扣方案。

#### 3. 角色映射

| 策略模式角色 | 题目中的类 |
|---|---|
| Context | `TicketContext` |
| Strategy | `DiscountStrategy` |
| ConcreteStrategy | `StudentDiscount`、`MilitaryDiscount`、`VipDiscount` |
| Client | 根据乘客身份选择策略的售票程序 |

#### 4. 类图/文字结构

```text
TicketContext o---- DiscountStrategy
                       ^
                       |
          +------------+-----------+
          |            |           |
 StudentDiscount  MilitaryDiscount  VipDiscount
```

#### 5. 关键代码

```java
public interface DiscountStrategy {
    double calculate(double originalPrice);
}

public final class StudentDiscount implements DiscountStrategy {
    public double calculate(double originalPrice) {
        return originalPrice * 0.5;
    }
}

public final class TicketContext {
    private DiscountStrategy strategy;

    public void setStrategy(DiscountStrategy strategy) {
        this.strategy = strategy;
    }

    public double getPrice(double originalPrice) {
        return strategy.calculate(originalPrice);
    }
}
```

#### 6. 体现的设计原则

- **OCP**：新增折扣只增加具体策略，不修改计价上下文。
- **DIP**：上下文面向 `DiscountStrategy` 接口编程。
- **SRP**：每个策略只负责一种折扣规则。
- **CRP**：用组合替代把折扣规则写入乘客继承体系。

#### 7. 优缺点与适用场景

优点：替代多重 `if-else`，折扣算法可独立扩展、测试和切换。  
缺点：客户端需要负责选择策略，策略类数量增加。  
适用：存在多种相互替换的计价、排序、压缩或路由算法。

> **关联资料**：[课件-策略模式](../../课件/02策略模式.pdf)

## 设计题3：Adapter + Strategy + Observer - 游戏角色通知

**【2019】** 游戏中有人类角色（骑士、骑兵、步兵），持有武器并通过 `fight()` 攻击；非人类角色巨魔也能持有武器，但攻击方法为 `beat()`。现在希望让巨魔和人类角色一起游戏，并在角色死亡时通知其他存活角色。

> 出处：[Exam0-往年考试.pdf#p11](../往年题/Exam0-往年考试.pdf#page=11)

### 参考答案（采用模板 4.5）

#### 1. 识别变化点

- **对象如何接入统一结构**：巨魔的 `beat()` 与游戏要求的 `attack()`/`fight()` 接口不兼容。
- **行为如何变化**：不同武器或攻击动作需要可替换。
- **对象如何协作**：一个角色死亡后，要通知多个仍存活角色。

本题没有明显的对象创建变化，因此不必强行加入创建型模式。

#### 2. 模式分工

| 子问题 | 模式 | 作用 |
|---|---|---|
| 巨魔接口不兼容 | **Adapter** | 把 `Troll.beat()` 适配为统一的 `GameRole.attack()` |
| 攻击/武器行为变化 | **Strategy** | 把攻击算法封装为 `AttackBehavior` |
| 死亡事件广播 | **Observer** | 角色死亡时通知所有注册的存活角色 |

#### 3. 为什么要组合

- Adapter 只解决接口兼容问题。
- Strategy 只解决攻击行为变化问题。
- Observer 只解决一对多事件通知问题。
- 三者分别负责结构、行为变化与对象协作，职责清晰，避免一个模式承担所有问题。

#### 4. 类图/角色映射

```text
GameRole <|.. HumanRole
GameRole <|.. TrollAdapter ----> Troll.beat()

GameRole o---- AttackBehavior
                   ^
                   +-- SwordAttack
                   +-- BowAttack

DeathSubject ---- notifies ----> DeathObserver
GameRole implements DeathObserver
```

- Adapter：Target=`GameRole`，Adapter=`TrollAdapter`，Adaptee=`Troll`。
- Strategy：Context=`GameRole`，Strategy=`AttackBehavior`。
- Observer：Subject=`GameSession/DeathPublisher`，Observer=`GameRole`。

#### 5. 关键伪代码

```java
interface GameRole extends DeathObserver {
    void attack();
    boolean isAlive();
}

final class TrollAdapter implements GameRole {
    private final Troll troll;

    public void attack() {
        troll.beat();
    }

    public void onDeath(GameRole deadRole) {
        // 更新界面、仇恨值或游戏状态
    }
}

final class DeathPublisher {
    private final List<GameRole> roles = new ArrayList<>();

    public void roleDied(GameRole deadRole) {
        for (GameRole role : roles) {
            if (role != deadRole && role.isAlive()) {
                role.onDeath(deadRole);
            }
        }
    }
}
```

#### 6. 设计原则与取舍

- **OCP**：增加角色适配器、攻击策略或观察者时无需修改发布者核心逻辑。
- **DIP**：游戏依赖 `GameRole`、`AttackBehavior`、`DeathObserver` 抽象。
- **SRP**：适配、攻击、通知各由不同对象负责。
- **CRP**：角色组合攻击行为。
- 代价：模式与对象数量增加，死亡通知顺序和观察者生命周期需要管理。

> **关联资料**：[pmx-观察者模式](../../旧课件/pmx/06观察者与行为型模式.pdf)；[课件-策略模式](../../课件/02策略模式.pdf)；[pmx-适配器](../../旧课件/pmx/07适配器与组合.pdf)

## 设计题4：Composite + Observer - 大学通知系统

**【2021】【2022】** 大学由若干院系组成，每个学生和老师属于某个院系，形成树状组织。管理员希望向某些部门或个人发送通知。

> 出处：[2021痛苦回忆#p1](../往年题/2021%20痛苦回忆.pdf#page=1)、[2022试卷#p2](../往年题/软统2022试卷.pdf#page=2)

### 参考答案（采用模板 4.5）

#### 1. 识别变化点

- **结构变化**：大学、院系和个人组成树，需要统一处理整体与叶子。
- **协作变化**：管理员发布通知后，订阅者需要收到更新。
- 对象创建不是题目重点，不必额外使用工厂模式。

#### 2. 模式分工

- **Composite**：`OrganizationUnit` 是 Component，`Department` 是 Composite，`Person` 是 Leaf。
- **Observer**：`NoticePublisher` 是 Subject，组织节点/个人是 Observer。

#### 3. 为什么要组合

Composite 负责“通知目标的树形组织”，Observer 负责“通知发布与接收解耦”。只用 Composite 会把发布者和组织遍历绑在一起；只用 Observer 又不能自然表示院系层级。

#### 4. 类图/角色映射

```text
NoticePublisher ---- notifies ----> NoticeObserver
                                          ^
                                          |
                               OrganizationUnit
                                 ^           ^
                                 |           |
                           Department      Person
                           (Composite)      (Leaf)
                               |
                               +-- children: List<OrganizationUnit>
```

#### 5. 关键代码

```java
public interface OrganizationUnit {
    void receive(String message);
}

public final class Department implements OrganizationUnit {
    private final List<OrganizationUnit> children = new ArrayList<>();

    public void add(OrganizationUnit child) {
        children.add(child);
    }

    public void receive(String message) {
        for (OrganizationUnit child : children) {
            child.receive(message);
        }
    }
}

public final class Person implements OrganizationUnit {
    private final String name;

    public void receive(String message) {
        System.out.println(name + " received: " + message);
    }
}

public final class NoticePublisher {
    private final List<OrganizationUnit> targets = new ArrayList<>();

    public void subscribe(OrganizationUnit target) {
        targets.add(target);
    }

    public void publish(String message) {
        targets.forEach(target -> target.receive(message));
    }
}
```

#### 6. 设计原则与取舍

- **OCP**：可增加新的组织节点或个人类型。
- **DIP**：发布者依赖 `OrganizationUnit` 抽象。
- **SRP**：发布者负责发布，组合节点负责层级传播，叶子负责接收。
- **CRP**：院系通过组合子节点形成组织树。
- 代价：大树递归通知可能重复或耗时，需要处理循环引用、重复订阅和权限过滤。

> **关联资料**：[pmx-适配器组合](../../旧课件/pmx/07适配器与组合.pdf)；[pmx-观察者模式](../../旧课件/pmx/06观察者与行为型模式.pdf)

## 设计题5：Command + Composite - 组合命令（宏命令）

**【2021】** 什么是组合命令（又称宏命令）？写出组合命令类的大致代码。

> 出处：[2021痛苦回忆#p1](../往年题/2021%20痛苦回忆.pdf#page=1)

### 参考答案（采用模板 4.5）

#### 1. 识别变化点

- **行为如何封装**：每个请求需要作为对象执行、撤销或排队。
- **对象如何组织**：多个命令要组成一个整体，并像单个命令一样执行。

#### 2. 模式分工

- **Command**：把请求封装为 `Command` 对象。
- **Composite**：`MacroCommand` 保存一组 `Command`，并实现同一接口。

#### 3. 为什么要组合

Command 使调用者与接收者解耦；Composite 使单个命令与命令集合能够被一致处理。因此宏命令既可以加入其他宏命令，也可以由同一个 Invoker 执行。

#### 4. 类图/角色映射

```text
Invoker ----> Command <|.. ConcreteCommand ----> Receiver
                  ^
                  |
             MacroCommand
             - children: List<Command>
```

#### 5. 关键代码

```java
public interface Command {
    void execute();
    void undo();
}

public final class MacroCommand implements Command {
    private final List<Command> commands = new ArrayList<>();

    public void add(Command command) {
        commands.add(command);
    }

    public void execute() {
        commands.forEach(Command::execute);
    }

    public void undo() {
        for (int i = commands.size() - 1; i >= 0; i--) {
            commands.get(i).undo();
        }
    }
}
```

#### 6. 设计原则与取舍

- **OCP**：新增具体命令无需修改 Invoker 或宏命令。
- **DIP**：Invoker 和 `MacroCommand` 都依赖 `Command` 抽象。
- **SRP**：具体命令负责请求，Invoker 负责触发，宏命令负责组合。
- **CRP**：通过组合构建复杂命令。
- 代价：命令类数量增加；撤销必须逆序，并处理部分命令失败后的回滚问题。

> **关联资料**：[pmx-状态命令模式](../../旧课件/pmx/05状态与命令模式.pdf)

## 设计题6：Pipe-and-Filter - 文本处理

**【2021】** 设计一个基于管道-过滤器模式的程序：输入文本文件，输出排序后的无重复单词列表。

> 出处：[2021痛苦回忆#p1](../往年题/2021%20痛苦回忆.pdf#page=1)

### 参考答案（参照模板 4.4）

> Pipe-and-Filter 是架构模式，不是 GoF 设计模式；这里沿用 4.4 的答题顺序组织答案。

#### 1. 使用的模式

使用 **Pipe-and-Filter（管道-过滤器）模式**。

#### 2. 模式意图

把文本处理拆成多个独立过滤步骤，通过管道传递统一格式的数据，使步骤可组合、替换和复用。

#### 3. 角色映射

| 模式角色 | 题目中的组件 |
|---|---|
| Source | `FileReader` |
| Filter | `Splitter`、`DuplicateRemover`、`Sorter` |
| Pipe | 过滤器之间的数据流/流对象 |
| Sink | 输出文件或控制台 |
| Pipeline | 负责连接并执行过滤器 |

#### 4. C&C 图

```text
[Input File]
    -> FileReader
    -> Splitter
    -> DuplicateRemover
    -> Sorter
    -> [Output]
```

每个箭头是 Pipe，每个处理框是 Filter。

#### 5. 关键代码

```java
public interface Filter<I, O> {
    O process(I input);
}

Filter<String, List<String>> splitter =
        text -> Arrays.asList(text.split("\\s+"));

Filter<List<String>, Set<String>> deduplicator =
        words -> new LinkedHashSet<>(words);

Filter<Set<String>, List<String>> sorter = words -> {
    List<String> result = new ArrayList<>(words);
    Collections.sort(result);
    return result;
};
```

#### 6. 体现的设计原则

- **SRP**：每个 Filter 只完成一个处理步骤。
- **OCP**：可以插入新的 Filter，而不改已有 Filter。
- **DIP**：Pipeline 面向统一 Filter 接口编程。
- **CRP**：通过组合过滤器形成完整处理流程。

#### 7. 优缺点与适用场景

优点：高内聚、低耦合，步骤易测试、复用、替换和并行化。  
缺点：数据格式转换有开销，不适合频繁交互或共享全局状态的系统。  
适用：编译器、ETL、日志处理、数据清洗和流式处理。

> **关联资料**：[旧课件-架构模式](../../旧课件/2025_UG_SysArch4_patterns.pdf)；[笔记-系统架构#p34](../笔记/软件系统设计-系统架构.pdf#page=34)

## 设计题7：Observer + Adapter - 分布式缓存同步

**【2015】【2019】【2022】反复出现** 在线客户服务系统有 N 台服务器，每台服务器有缓存。缓存更新时，变更必须提交数据库，并使其他缓存失效后重新加载。异构服务器可能使用不同通信协议。

> 出处：[2015真题第3页](../往年题/2015/3.jpg)、[2022试卷#p2](../往年题/软统2022试卷.pdf#page=2)、[Exam0-往年考试.pdf#p12](../往年题/Exam0-往年考试.pdf#page=12)

### 参考答案（采用模板 4.5）

#### 1. 识别变化点

- **协作变化**：任一缓存更新后，要一对多通知其他缓存。
- **结构/接口变化**：不同服务器可能使用 RMI、HTTP、SOAP 等不兼容协议。
- 对象创建不是本题主要矛盾。

#### 2. 模式分工

- **Observer**：负责缓存变更的一对多通知。
- **Adapter**：把异构协议统一为 `CacheConnector` 接口。

#### 3. 为什么要组合

Observer 解决“通知谁”，Adapter 解决“如何以统一接口通知”。若只使用 Observer，协调器仍会依赖各服务器的具体协议；加入 Adapter 后，协调器只依赖抽象连接器。

#### 4. 角色映射与结构

| 模式 | 角色 | 系统元素 |
|---|---|---|
| Observer | Subject | `CacheCoordinator` |
| Observer | Observer | 各服务器的 `CacheNode` |
| Adapter | Target | `CacheConnector` |
| Adapter | Adapter | `RmiCacheAdapter`、`HttpCacheAdapter`、`SoapCacheAdapter` |
| Adapter | Adaptee | 各异构缓存服务 |

```text
Cache1 -> Database: commit
Cache1 -> CacheCoordinator: changed(cache1)
CacheCoordinator -> CacheConnector2: invalidateAndReload()
CacheCoordinator -> CacheConnector3: invalidateAndReload()

CacheConnector <|.. RmiCacheAdapter  -> RMI Cache
CacheConnector <|.. HttpCacheAdapter -> HTTP Cache
CacheConnector <|.. SoapCacheAdapter -> SOAP Cache
```

#### 5. 关键伪代码

```java
interface CacheConnector {
    String id();
    void invalidateAndReload();
}

final class CacheCoordinator {
    private final List<CacheConnector> caches = new ArrayList<>();

    public void cacheChanged(String sourceId) {
        for (CacheConnector cache : caches) {
            if (!cache.id().equals(sourceId)) {
                cache.invalidateAndReload();
            }
        }
    }
}
```

#### 6. 设计原则与取舍

- **OCP**：增加缓存节点或协议适配器无需修改协调器。
- **DIP**：协调器依赖 `CacheConnector` 抽象。
- **SRP**：协调器负责通知，Adapter 负责协议转换，Cache 负责缓存。
- 代价：协调器可能成为单点；同步广播可能放大延迟，应考虑消息队列、重试、幂等和失效版本号。

> **关联资料**：[pmx-观察者模式](../../旧课件/pmx/06观察者与行为型模式.pdf)；[旧课件-架构模式](../../旧课件/2025_UG_SysArch4_patterns.pdf)

## 设计题8：Multi-instance 模式

**【2022】** 设计 Multi-instance 模式，保证系统中某类对象数量不超过常量 n，并写出实现代码。

> 出处：[2022试卷#p2](../往年题/软统2022试卷.pdf#page=2)

### 参考答案（采用模板 4.4）

#### 1. 使用的模式

使用 **Multi-instance（多例模式）**，可视为 Singleton 从“最多 1 个”推广到“最多 n 个”。

#### 2. 模式意图

集中控制实例创建和访问，确保实例总数存在固定上限，并在达到上限后复用已有实例。

#### 3. 角色映射

- `MultiInstance`：受控创建的类。
- `instances`：保存全部实例的静态池。
- `getInstance()`：统一访问和创建入口。
- Client：不能直接调用构造方法，只能通过静态入口取得对象。

#### 4. 结构

```text
Client ----> MultiInstance.getInstance()
                 |
                 +-- static instances[0..n-1]
                 +-- private constructor
```

#### 5. 关键代码

```java
public final class MultiInstance {
    private static final int MAX_COUNT = 3;
    private static final List<MultiInstance> INSTANCES = new ArrayList<>();
    private static int nextIndex = 0;

    private MultiInstance() {}

    public static synchronized MultiInstance getInstance() {
        if (INSTANCES.size() < MAX_COUNT) {
            INSTANCES.add(new MultiInstance());
        }
        MultiInstance result = INSTANCES.get(nextIndex);
        nextIndex = (nextIndex + 1) % INSTANCES.size();
        return result;
    }
}
```

#### 6. 体现的设计原则

- 封装构造过程，保证数量约束始终成立。
- 客户端只依赖统一获取入口。
- 若希望更符合 DIP，可让客户端依赖对象池/提供者接口，而不是直接调用静态方法。

#### 7. 优缺点与适用场景

优点：严格控制实例数量并复用昂贵资源。  
缺点：引入全局状态；并发、回收和负载分配复杂；静态入口不利于测试。  
适用：连接池、线程池、有限设备句柄等资源受限场景。

> **关联资料**：[课件-创建型模式](../../课件/04创建型模式.pdf)；[pmx-创建型模式](../../旧课件/pmx/04创建型模式.pdf)

## 设计题9：Observer + Strategy - 条件化多渠道通知

**【2025】** 设计通知系统，通过多个通知渠道通知利益相关者；不同渠道只有在运行时条件满足时才能使用，并且系统应避免生成不会被使用的信息。

> 出处：[2025期末](../往年题/软统25期末-不完全准确.jpeg)

### 参考答案（采用模板 4.5）

#### 1. 识别变化点

- **协作变化**：一次业务事件要通知多个利益相关者/渠道。
- **行为变化**：Email、SMS、Push、WeChat 的发送方式不同。
- **运行时条件变化**：每个渠道有不同的可用条件。
- **惰性生成**：条件不满足时不得提前生成对应消息。

#### 2. 模式分工

- **Observer**：业务事件发布者通知多个渠道观察者。
- **Strategy**：每种渠道使用独立的发送/消息生成策略。
- `ChannelCondition` 是策略式条件对象；只有条件满足后才调用消息工厂，避免无用信息。

> 不必为了“多模式”而强行加入 Decorator。若题目明确要求动态叠加加密、重试、审计等横切功能，再考虑 Decorator。

#### 3. 为什么要组合

Observer 解决“一对多通知”，Strategy 解决“渠道算法可替换”，条件策略解决“是否发送”。组合后可独立增加渠道、条件和消息格式。

#### 4. 类图/角色映射

```text
NotificationSubject ---- notifies ----> ChannelObserver
                                             |
                                             +-- condition: ChannelCondition
                                             +-- sender: SendStrategy
                                             +-- factory: MessageFactory

SendStrategy <|.. EmailSender / SmsSender / PushSender
```

#### 5. 关键代码

```java
final class ChannelObserver {
    private final ChannelCondition condition;
    private final MessageFactory messageFactory;
    private final SendStrategy sender;

    public void update(Event event) {
        if (!condition.isSatisfied(event)) {
            return;
        }
        // 条件通过后才生成消息，避免产生用不到的信息。
        Message message = messageFactory.create(event);
        sender.send(message);
    }
}
```

#### 6. 设计原则与取舍

- **OCP**：新增渠道、条件或消息策略无需修改发布者。
- **DIP**：发布者和渠道依赖 Observer/Strategy 抽象。
- **SRP**：条件判断、消息生成、消息发送分离。
- **CRP**：渠道观察者组合条件、工厂和发送策略。
- 代价：配置关系增多；需要处理通知顺序、失败重试、重复发送和观察者注销。

> **关联资料**：[pmx-观察者模式](../../旧课件/pmx/06观察者与行为型模式.pdf)；[课件-策略模式](../../课件/02策略模式.pdf)

## 设计题10：外卖平台微服务设计

**【2025】** 外卖平台为什么适合使用微服务？说明微服务拆分及其具体应用。

> 出处：[2025期末](../往年题/软统25期末-不完全准确.jpeg)

### 参考答案（参照模板 4.5）

> 本题组合的是多个微服务架构模式，不是 GoF 设计模式；仍使用“变化点 -> 模式分工 -> 组合理由 -> 结构 -> 取舍”的顺序作答。

#### 1. 识别变化点

- **业务能力变化**：用户、商家、订单、支付、配送、通知可独立演进。
- **规模变化**：浏览、下单和支付的流量特征不同，需要独立扩缩。
- **协作变化**：服务既有同步查询，也有异步订单事件。
- **可靠性变化**：单个服务失败不能拖垮整个平台。

#### 2. 服务拆分与模式分工

| 业务能力 | 微服务 | 主要职责 |
|---|---|---|
| 用户注册/登录 | User Service | 用户资料、认证 |
| 餐厅/菜单 | Merchant Service | 商家和菜品 |
| 下单 | Order Service | 订单创建与状态 |
| 支付/退款 | Payment Service | 支付渠道和退款 |
| 配送调度 | Delivery Service | 骑手调度与路径 |
| 消息推送 | Notification Service | SMS、Push、站内信 |

核心架构模式：

- **API Gateway**：统一入口、认证、路由和限流。
- **Service Registry/Discovery**：服务动态定位。
- **Circuit Breaker**：防止级联故障。
- **Database per Service**：服务拥有独立数据。
- **Saga/Event-driven**：处理跨服务业务流程和最终一致性。

#### 3. 为什么要组合

单一模式无法同时解决入口治理、服务定位、故障隔离和数据一致性。上述模式分别解决不同分布式问题，共同形成可运行的微服务架构。

#### 4. C&C 结构

```text
Client -> API Gateway
             |
             +-> User Service -> User DB
             +-> Merchant Service -> Merchant DB
             +-> Order Service -> Order DB
             +-> Payment Service -> Payment DB
             +-> Delivery Service -> Delivery DB

Order Service -> Event Bus -> Payment / Delivery / Notification
All Services <-> Service Registry
```

#### 5. 关键流程伪代码

```text
1. Gateway 将下单请求路由到 Order Service。
2. Order Service 创建 PENDING 订单并发布 OrderCreated。
3. Payment Service 消费事件并完成支付，发布 PaymentSucceeded/Failed。
4. Delivery Service 在支付成功后创建配送任务。
5. Notification Service 异步通知用户。
6. 任一步失败时由 Saga 执行补偿操作。
```

#### 6. 设计原则与质量属性

- **SRP/高内聚**：每个服务围绕一个业务能力。
- **DIP**：服务通过契约和事件交互，不依赖其他服务内部实现。
- **可修改性**：服务可以独立演进和部署。
- **可伸缩性**：热点服务可独立扩容。
- **可用性**：熔断、限流、降级和冗余部署。
- **性能**：缓存、异步事件和负载均衡。

#### 7. 优缺点与适用场景

优点：支持多团队并行、独立部署、独立扩缩和故障隔离。  
缺点：增加网络开销、运维成本、链路追踪和分布式一致性难度。  
适用：业务复杂、团队较多、模块负载差异明显且需要频繁发布的平台。
