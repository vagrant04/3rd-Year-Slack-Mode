# 09-总结与思考（第58-59页）

> 本章总结面向对象设计的7大原则，并展示它们之间的层次关系

---

## 第58页 - 小结（上）

### 📋 核心观点

**对于面向对象的软件系统设计来说**：
- 在支持**可维护性**的同时
- 需要提高系统的**可复用性**

**软件复用的价值**：
- 软件的复用可以提高软件的**开发效率**
- 提高软件**质量**
- 节约**开发成本**
- 恰当的复用还可以改善系统的**可维护性**

### 📋 7个原则的一句话总结

**单一职责原则（SRP）**：
- 在软件系统中，一个类只负责**一个功能领域**中的相应职责

**开闭原则（OCP）**：
- 一个软件实体应当**对扩展开放，对修改关闭**
- 即在**不修改源代码**的基础上扩展一个系统的行为

**里氏代换原则（LSP）**：
- 可以通俗表述为在软件中如果能够使用基类对象
- 那么一定能够使用其**子类对象**

**依赖倒转原则（DIP）**：
- 抽象不应该依赖于**细节**
- 细节应该依赖于**抽象**
- 要**针对接口编程**，不要针对实现编程

**接口隔离原则（ISP）**：
- 客户端不应该依赖那些它**不需要的接口**
- 即将一些大的接口细化成一些**小的接口**供客户端使用

**合成复用原则（CRP）**：
- 复用时尽量使用**对象组合**，而不使用**继承**

**迪米特法则（LoD）**：
- 一个软件实体应当**尽可能少的**与其他实体发生相互作用

### 📊 原则之间的关系网络

**核心关系**：
```
目标: OCP (对扩展开放，对修改关闭)
  ↓
主要手段: DIP (依赖抽象而非具体)
  ↓
重要方式: LSP (子类可替换父类)
  ↓
基础: SRP (单一职责)
  ↓
辅助: ISP (接口隔离) + CRP (组合复用) + LoD (最少知识)
```

**相互支持关系**：
```
SRP ─────→ ISP  (职责单一 → 接口隔离)
 │
 └────→ OCP  (职责单一 → 易于扩展)

DIP ─────→ OCP  (依赖抽象 → 对修改关闭)
 │
 └────→ LSP  (依赖抽象的前提是LSP)

CRP ─────→ LoD  (组合 → 降低耦合)
 │
 └────→ OCP  (组合 → 易于扩展)

LoD ─────→ OCP  (低耦合 → 易于扩展)
```

## 综合理解

### 💡 如何综合运用7个原则

**设计一个新系统的步骤**：

1. **第一步：明确目标（OCP）**
   - 问自己："哪些部分将来可能变化？"
   - 这些部分要设计成对扩展开放、对修改关闭

2. **第二步：识别职责（SRP）**
   - 问自己："这个类有几个变化原因？"
   - 如果多于1个，考虑拆分

3. **第三步：抽象化（DIP）**
   - 问自己："能否定义一个抽象？"
   - 让高层和低层都依赖抽象

4. **第四步：检查继承（LSP）**
   - 问自己："子类能完全替换父类吗？"
   - 如果不能，考虑重新设计继承关系

5. **第五步：考虑复用方式（CRP）**
   - 问自己："这是has-a还是is-a关系？"
   - 优先使用组合而非继承

6. **第六步：细化接口（ISP）**
   - 问自己："这个接口是否太大？"
   - 如果客户端只需要部分方法，考虑拆分

7. **第七步：降低耦合（LoD）**
   - 问自己："这个类知道的是否太多？"
   - 只与直接朋友通信

### 🎯 重构现有系统的顺序

**遇到问题时的诊断顺序**：

1. **识别坏味道**
   - 添加新功能需要修改多处代码 → 违反**OCP**
   - 一个类有多个修改原因 → 违反**SRP**
   - 依赖具体类 → 违反**DIP**
   - 子类不能替换父类 → 违反**LSP**
   - 继承导致耦合太紧 → 违反**CRP**
   - 接口太大 → 违反**ISP**
   - 类之间依赖太多 → 违反**LoD**

2. **确定重构方向**
   - 针对性地应用相应的原则

3. **逐步重构**
   - 小步前进，每次改进一个原则
   - 重构后立即测试

## 经典案例回顾

### 📋 按钮系统（OCP+DIP+LSP）

**问题**：切换按钮样式需要修改代码

**应用的原则**：
1. **OCP**：通过抽象使系统对扩展开放
2. **DIP**：LoginForm依赖抽象的AbstractButton
3. **LSP**：CircleButton和RectangleButton可以替换AbstractButton

**关键设计**：
- 定义AbstractButton抽象类
- 具体按钮类继承AbstractButton
- LoginForm依赖AbstractButton
- 配置文件指定具体按钮

### 📋 DAO系统（CRP+LoD）

**问题**：DAO继承DBUtil导致耦合太紧

**应用的原则**：
1. **CRP**：改继承为组合
2. **LoD**：DAO不直接创建DBUtil，通过注入

**关键设计**：
- StudentDAO/TeacherDAO持有DBUtil对象
- 通过组合而非继承复用DBUtil

### 📋 Form-DAO系统（LoD）

**问题**：Form直接依赖多个DAO，耦合复杂

**应用的原则**：
1. **LoD**：Form只与Controller通信
2. **SRP**：Controller负责协调Form和DAO

**关键设计**：
- 引入Controller中介者
- Form只知道Controller
- Controller负责调用DAO

## 常见误区

### ⚠️ 误区1：过度设计

❌ **错误观点**："必须严格遵守所有原则"

✅ **正确认识**：
- 原则是指导方针，不是绝对规则
- 要在灵活性和复杂性之间平衡
- 简单的模块不需要过度抽象

### ⚠️ 误区2：原则冲突

❌ **错误观点**："ISP要求拆分接口，但会增加类的数量"

✅ **正确认识**：
- 原则之间不是对立的，而是互补的
- ISP增加的是接口数量，不是实现类数量
- 拆分接口降低了耦合，符合LoD

### ⚠️ 误区3：一步到位

❌ **错误观点**："一开始就要设计完美的架构"

✅ **正确认识**：
- 先写简单的代码
- 当发现频繁变化时再重构
- 渐进式改进，而非一步到位

## 实践建议

### 💡 学习路径

1. **理解定义**（1周）
   - 背诵7个原则的定义
   - 理解基本概念

2. **识别坏味道**（2周）
   - 在现有代码中识别违反原则的地方
   - 练习判断违反了哪个原则

3. **重构实践**（4周）
   - 小步重构，每次改进一个原则
   - 重构后对比效果

4. **综合应用**（持续）
   - 在新项目中从设计阶段就考虑原则
   - 在代码评审中检查是否符合原则

### 💡 实战技巧

1. **代码评审时**
   - 检查是否违反SRP（一个类多个职责）
   - 检查是否违反OCP（if-else判断类型）
   - 检查是否违反DIP（依赖具体类）

2. **设计新功能时**
   - 先思考可变因素（EVP）
   - 再定义抽象（DIP）
   - 然后实现具体类（LSP）

3. **维护旧代码时**
   - 识别最严重的坏味道
   - 优先重构高频变化的部分
   - 小步迭代，保持测试通过

## 最终总结

### 🎯 核心要点

**7个原则**：
- **SRP**：一个类一个职责
- **OCP**：对扩展开放，对修改关闭
- **LSP**：子类可替换父类
- **DIP**：依赖抽象，不依赖具体
- **ISP**：接口隔离，不要胖接口
- **CRP**：组合优于继承
- **LoD**：只与朋友通信

**层次关系**：
- 目标：OCP
- 指导：LoD + EVP
- 基础：SRP
- 实现：DIP + LSP + CRP + ISP

**记忆口诀**：
> **"单开里依接合迪"**
> **"开闭为目标，依赖是手段"**
> **"单一是基础，四将来实现"**
