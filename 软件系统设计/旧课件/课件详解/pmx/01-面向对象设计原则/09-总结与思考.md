## 📄 第58页 - 思考题

### 思考题内容
**问题**: 在JDK中，`java.util.Stack`是`java.util.Vector`类的子类，该设计合理吗？若不合理，请分析解释该设计存在的问题。

### 问题分析
这是一个经典的**违反LSP**的案例！

#### Stack继承Vector的问题
```java
public class Stack<E> extends Vector<E> {
    public E push(E item) { ... }
    public E pop() { ... }
    // 继承了Vector的所有方法
}
```

❌ **设计问题**:
1. **违反LSP**: Stack不能真正替换Vector
   - Stack是后进先出 (LIFO)
   - Vector是随机访问
   - 语义不兼容

2. **破坏封装**: 继承了Vector的public方法
   ```java
   Stack<Integer> stack = new Stack<>();
   stack.push(1);  // 应该从栈顶添加
   stack.add(0, 2);  // 但可以从任意位置添加！违反了Stack的语义
   stack.remove(1);  // 可以从任意位置删除！破坏了LIFO
   ```

3. **违反SRP**: Stack继承了不需要的方法
   - `get(int index)`, `set(int index)`, `add(int index, E element)` 等
   - 这些方法不应该在Stack中暴露

#### 正确设计 (使用组合)
```java
class Stack<E> {
    private List<E> elements = new ArrayList<>();  // 组合而非继承

    public void push(E item) {
        elements.add(item);
    }

    public E pop() {
        return elements.remove(elements.size() - 1);
    }

    public E peek() {
        return elements.get(elements.size() - 1);
    }

    // 不暴露List的其他方法
}
```

### 设计原则分析
这个案例违反了：
- ❌ **LSP**: Stack不能替换Vector
- ❌ **ISP**: Stack继承了不需要的接口
- ❌ **CRP**: 应该用组合而非继承

### 考点提示
⚠️ **高频考点**: Stack继承Vector的问题是经典面试题和考试题！

## 📄 第59页 - 设计原则小结 ⭐⭐⭐⭐⭐

### 小结内容 (第1部分)
**复用与可维护性**:
- 对于面向对象的软件系统设计来说，在支持可维护性的同时，需要提高系统的可复用性
- 软件的复用可以提高软件的开发效率，提高软件质量，节约开发成本，恰当的复用还可以改善系统的可维护性

**各原则要点**:
- **SRP**: 一个类只负责一个功能领域中的相应职责
- **OCP**: 一个软件实体应当对扩展开放，对修改关闭
- **LSP**: 在软件中如果能够使用基类对象，那么一定能够使用其子类对象

---

## 📄 第59页 - 设计原则小结 (第2部分)

### 小结内容 (续)
- **DIP**: 抽象不应该依赖于细节，细节应该依赖于抽象；要针对接口编程，不要针对实现编程
- **ISP**: 客户端不应该依赖那些它不需要的接口
- **CRP**: 复用时尽量使用对象组合，而不使用继承
- **LoD**: 一个软件实体应当尽可能少的与其他实体发生相互作用

## 📄 第59页 - 原则间的关系 ⭐⭐⭐⭐⭐

### 关系图
```
        【目标】开闭原则 (OCP)
               ↑
       ┌───────┼───────┐
       │       │       │
   【指导】 【基础】 【实现】
     LoD   SRP+EVP  DIP+CRP+LSP+ISP
```

### 层次解析
1. **目标层**: **开闭原则 (OCP)**
   - 这是我们设计的终极目标
   - 系统对扩展开放，对修改关闭

2. **指导层**: **迪米特法则 (LoD)**
   - 设计过程的指导思想
   - 降低耦合，信息隐藏

3. **基础层**: **单一职责 (SRP) + 可变性封装 (EVP)**
   - 设计的基础
   - 职责单一才能清晰抽象

4. **实现层**: **DIP + CRP + LSP + ISP**
   - 实现OCP的具体手段
   - **DIP**: 依赖抽象 → 可扩展
   - **CRP**: 组合复用 → 灵活性
   - **LSP**: 子类可替换 → 多态
   - **ISP**: 接口隔离 → 低耦合

### 原则协作关系

#### OCP的实现路径
```
1. SRP分离职责 → 2. 识别可变点 (EVP) → 3. 提取抽象 (DIP)
         ↓                  ↓                    ↓
4. 子类实现 (LSP) → 5. 使用组合 (CRP) → 6. 接口专一 (ISP)
         ↓                  ↓                    ↓
                    7. 实现OCP ✅
```

#### 相互支持关系
- **SRP + DIP**: 职责单一 → 容易抽象接口
- **DIP + LSP**: 依赖抽象 → 需要子类可替换
- **LSP + OCP**: 子类可替换 → 可扩展不需修改
- **CRP + DIP**: 组合复用 → 依赖接口而非具体类
- **ISP + SRP**: 接口单一 → 职责清晰
- **LoD + All**: 降低耦合 → 支持所有原则

### 记忆口诀
```
目标: OCP (开闭)
指导: LoD (迪米特)
基础: SRP (单一职责)
手段: DIP (依赖倒转)
支撑: LSP + CRP + ISP
```

### 设计流程
**实际设计时的思维顺序**:
1. 分析职责 → 应用**SRP**
2. 识别变化点 → 应用**EVP**
3. 提取抽象 → 应用**DIP**
4. 设计继承 → 遵守**LSP**
5. 选择复用方式 → 应用**CRP**
6. 设计接口 → 应用**ISP**
7. 降低耦合 → 应用**LoD**
8. 达到目标 → 实现**OCP**
