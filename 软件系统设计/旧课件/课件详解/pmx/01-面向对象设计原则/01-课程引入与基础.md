## 第2页 - 软件设计

### 📋 内容要点

软件开发的四个层次：

1. **需求（Requirement）**
   - 定义了系统需要满足的目标

2. **规约（Specification）**
   - 定义了系统的外部可观察到的行为

3. **架构（Architecture）**
   - 定义了系统一级的主要组成部分
   - 各部分的交互方法
   - 使用的技术

4. **设计（Design）**
   - 定义了如何完成任务
   - 需要写的代码
   - 我们将专门关注OO设计

### 💡 理解要点

这是一个**自顶向下**的层次关系：

```
需求（What）
  ↓
规约（Behavior）
  ↓
架构（Structure）
  ↓
设计（How）
```

- **需求**回答"做什么"（用户需要什么功能）
- **规约**回答"表现如何"（系统行为是否符合需求）
- **架构**回答"大结构"（模块如何划分）
- **设计**回答"怎么做"（具体如何实现）

### ⚠️ 考点

- 能够区分需求、规约、架构、设计的含义
- 理解本课程聚焦于"设计"层，特别是"面向对象设计"

## 第4页 - 面向对象软件设计

### 📋 定义

面向对象软件设计（OOD）是指：
- 将**实现的约束条件**应用到面向对象分析所产生的**概念模型**的过程
- 用**方法**和**属性**来描述用于构成系统的类
- 添加不明显属于领域的类，比如**抽象类**和**接口**
- 描述类是如何构成组件的

### 💡 理解要点

OOD的三个核心工作：

1. **细化类的内部结构**
   - OOA阶段只识别出类和关系
   - OOD阶段要确定每个类的属性和方法

2. **引入技术类**
   - 领域类：来自问题域（如Student、Teacher）
   - 技术类：支撑实现（如AbstractButton、DatabaseConnection）

3. **确定类的组织方式**
   - 包（Package）的划分
   - 组件（Component）的划分

### ⚠️ 易混淆点

- **OOA**（分析）：识别领域概念，建立概念模型
- **OOD**（设计）：添加技术细节，准备编程实现
- **OOP**（编程）：用编程语言实现设计

## 第6页 - 如何发现合适的对象

### 📋 内容要点

OOD的难点在于将一个系统分解成对象。

**对象的来源**：

1. **来自分析模型**
   - 直接映射领域概念
   - 例如：Student、Course、Teacher

2. **来自实现空间**
   - 数据库（Database、Connection、Transaction）
   - 文件（FileReader、FileWriter）
   - 用户界面（Form、Button、TextField）
   - 进程间通信（IPC、Socket、Message）

3. **来自设计模式**
   - 用来使可能过于特殊的设计变得更为通用
   - 例如：使用"**策略模式**"
     - 如果你认为一个算法很可能会改变
     - 添加类来实现"策略"模式

### 💡 理解要点

**为什么难？**
- 领域对象容易识别（直接来自需求）
- 技术对象需要经验（需要知道各种设计模式和技术方案）

**策略模式示例**：
```java
// 不使用策略模式（糟糕设计）
class Calculator {
    public int calculate(int a, int b, String operator) {
        if (operator.equals("+")) {
            return a + b;
        } else if (operator.equals("-")) {
            return a - b;
        }
        // 每次新增运算符都要修改这个类
    }
}

// 使用策略模式（优秀设计）
interface Strategy {
    int execute(int a, int b);
}

class AddStrategy implements Strategy {
    public int execute(int a, int b) { return a + b; }
}

class Calculator {
    private Strategy strategy;
    public int calculate(int a, int b) {
        return strategy.execute(a, b);
    }
}
```

### ⚠️ 考点

- 能够说出对象的三个主要来源
- 理解为什么需要引入设计模式（使设计更通用）

## 第7页 - 经验至关重要

### 📋 内容要点

从OOA到OOD，没有循序渐进的简单方法。

```
     UML        ?         Architecture
     OOA    → magic? →        OOD         → OOP
(概念模型)              (设计模型)      (代码)
```

**关键点**：
- 至少OOA以相当直接的方式给出了问题域组件
- 对于其他的部分，则**需要经验**

### 💡 理解要点

**什么是"magic"？**
- 这是一个幽默的说法，表示从分析到设计没有机械的转换规则
- 需要设计师凭借经验做出判断：
  - 如何划分职责？
  - 如何选择设计模式？
  - 如何平衡各种设计原则？

**为什么需要经验？**
- OOA → OOD 的转换涉及大量设计决策
- 每个决策都会影响系统的质量
- 没有"银弹"，只能通过经验积累

### ⚠️ 考点

- 理解"从OOA到OOD没有简单方法"的含义
- 理解经验在面向对象设计中的重要性

## 第8页 - 经验如何而来

### 📋 内容要点

经验丰富的设计师看到**同样的老问题**一次又一次的出现：
- 如何设计我的**第五个**用户界面的类？
- 如何**第三次**设计支持持久化到数据库的类？
- 如何组织班级进行**第五次**汇报工作？
- ...

**经验的积累方式**：
- 每次遇到类似的问题，设计师一般都会从**之前行之有效的东西**入手
- 但通常会体会到上一次他们**可以做得更好**
- 技术在我们脚下不断变化，所以我们的设计经验**很快就被淘汰了**
- 但**设计原则**以及一些**经典的设计经验**不会褪色……

### 💡 理解要点

**为什么强调"第五个"、"第三次"？**
- 第一次：摸索着做，可能很糟糕
- 第二次：有了一些想法，但还不够成熟
- 第三次以后：开始形成经验，知道什么是好的设计

**什么会变？什么不变？**
- **会变**: 具体技术（数据库从MySQL到PostgreSQL）
- **不变**: 设计原则（依赖倒转原则永远适用）

**本课程的意义**：
- 总结前人的经验，形成设计原则
- 让你不用"试错5次"就能掌握好的设计方法

### ⚠️ 考点

- 理解为什么设计原则比具体技术更持久
- 理解设计原则是前人经验的总结

## 第10-14页 - 面向对象设计原则概述

### 📋 第10页：可维护性和可复用性

#### Robert C. Martin的观点

知名软件大师**Robert C. Martin**认为一个**可维护性较低**的软件设计，通常由于如下**4个原因**造成：

1. **过于僵硬（Rigidity）**
   - 系统难以改变
   - 每次改动都会影响系统的许多其他部分

2. **过于脆弱（Fragility）**
   - 对系统的某处修改会导致系统其他部分出错
   - 出错的地方往往与修改的地方没有明显的关联

3. **复用率低（Immobility）**
   - 系统中的某些部分本来可以在其他系统中复用
   - 但是分离这些部分所需的工作量太大

4. **黏度过高（Viscosity）**
   - 做正确的事情比做错误的事情更难
   - 当面临修改时，保持设计不变比破坏设计更困难

### 💡 理解要点

这四个特征可以用生活中的例子理解：

| 特征 | 类比 | 软件例子 |
|-----|------|---------|
| 僵硬 | 一块铁板，想改形状很难 | 修改一个类需要同时修改10个类 |
| 脆弱 | 玻璃制品，一碰就碎 | 修改登录模块导致报表模块出错 |
| 复用率低 | 零件被焊死在机器上 | 想复用一个工具类但它依赖了太多其他类 |
| 黏度过高 | 走正道要翻山，走歪路很平坦 | 正确地扩展系统需要3天，但hack一下只需1小时 |

---

### 📋 第11页：Peter Coad的观点

软件工程和建模大师**Peter Coad**认为，一个好的系统设计应该具备如下**3个性质**：

1. **可扩展性（Extensibility）**
   - 能够方便地添加新功能
   - 不需要大规模修改现有代码

2. **灵活性（Flexibility）**
   - 能够适应需求的变化
   - 能够支持多种不同的使用场景

3. **可插入性（Pluggability）**
   - 组件可以方便地替换
   - 类似于USB设备，可以随时插拔

### 💡 理解要点

**与Robert C. Martin观点的对比**：
- Martin从"反面"描述糟糕设计的特征
- Coad从"正面"描述优秀设计的特征
- 两者是一个硬币的两面

**可插入性示例**：
```java
// 糟糕设计：不可插入
class ReportGenerator {
    private MySQLDatabase db = new MySQLDatabase();
    // 数据库类型被写死，无法更换
}

// 优秀设计：可插入
class ReportGenerator {
    private Database db;  // 依赖抽象
    public void setDatabase(Database db) {
        this.db = db;  // 可以插入任何Database实现
    }
}
```

### 📋 第12页：软件复用的优点

软件的复用（Reuse）或重用拥有众多优点：
- 提高软件的**开发效率**
- 提高软件**质量**
- 节约**开发成本**
- 恰当的复用还可以改善系统的**可维护性**

**面向对象设计复用的目标**：
- 实现支持**可维护性**的复用

**原则与复用的关系**：
- 在面向对象的设计里面，**可维护性**复用都是以**面向对象设计原则**为基础的
- 这些设计原则首先都是**复用的原则**
- 遵循这些设计原则可以有效地提高系统的**复用性**，同时提高系统的**可维护性**

### 💡 理解要点

**可维护性与可复用性的关系**：
```
可复用性 ⇄ 可维护性
   ↑          ↑
   └─────┬────┘
      设计原则
```

- **好的复用** → 提高可维护性
  - 复用经过验证的组件，减少bug
  - 修改一处，多处受益

- **好的可维护性** → 提高可复用性
  - 容易理解的代码更容易被复用
  - 低耦合的模块更容易被提取复用

### 📋 第13页：重构与设计原则

面向对象设计原则也是对系统进行合理**重构**的指南针。

**重构（Refactoring）**的定义：
- 在**不改变软件现有功能**的基础上
- 通过调整程序代码**改善软件的质量、性能**
- 使其程序的**设计模式**和**架构**更趋合理
- 提高软件的**扩展性**和**维护性**

**Martin Fowler**：《重构：改善既有代码的设计》作者

### 💡 理解要点

**重构的关键特征**：
- ✅ 外部行为不变（功能不变）
- ✅ 内部结构改善（代码质量提升）
- ✅ 小步迭代（每次改一点）

**重构示例**：
```java
// 重构前：违反单一职责原则
class User {
    String name;
    String email;

    void saveToDatabase() {
        // 数据库保存逻辑
    }

    void sendEmail() {
        // 邮件发送逻辑
    }
}

// 重构后：符合单一职责原则
class User {
    String name;
    String email;
}

class UserRepository {
    void save(User user) {
        // 数据库保存逻辑
    }
}

class EmailService {
    void send(User user) {
        // 邮件发送逻辑
    }
}
```

**设计原则作为指南针**：
- 识别代码坏味道：发现违反了哪个原则
- 确定重构方向：朝着符合原则的方向改进
- 验证重构效果：重构后是否更符合原则

### 📋 第14页：7个设计原则简介

常用的面向对象设计原则包括**7个**，这些原则并不是孤立存在的，它们**相互依赖，相互补充**。

| 设计原则名称 | 设计原则简介 | 重要性 |
|------------|------------|--------|
| **单一职责原则**<br>Single Responsibility Principle, SRP | 类的职责要单一，不能将太多的职责放在一个类中 | ⭐⭐⭐⭐ |
| **开闭原则**<br>Open-Closed Principle, OCP | 软件实体对扩展是开放的，但对修改是关闭的，即在不修改一个软件实体的基础上去扩展其功能 | ⭐⭐⭐⭐⭐ |
| **里氏代换原则**<br>Liskov Substitution Principle, LSP | 在软件系统中，一个可以接受基类对象的地方必然可以接受一个子类对象 | ⭐⭐⭐⭐ |
| **依赖倒转原则**<br>Dependency Inversion Principle, DIP | 要针对抽象层编程，而不要针对具体类编程 | ⭐⭐⭐⭐⭐ |
| **接口隔离原则**<br>Interface Segregation Principle, ISP | 使用多个专门的接口来取代一个统一的接口 | ⭐⭐ |
| **合成复用原则**<br>Composite Reuse Principle, CRP | 在系统中应该尽量多使用组合和聚合关联关系，尽量少使用甚至不使用继承关系 | ⭐⭐⭐⭐ |
| **迪米特法则**<br>Law of Demeter, LoD | 一个软件实体对其他实体的引用越少越好，或者说如果两个类不必彼此直接通信，那么这两个类就不应当发生直接的相互作用，而是通过引入一个第三者发生间接交互 | ⭐⭐⭐ |

### 💡 重要性排序理解

**最重要（⭐⭐⭐⭐⭐）**：
- **OCP 开闭原则**：面向对象设计的**终极目标**
- **DIP 依赖倒转原则**：实现OCP的**主要手段**

**很重要（⭐⭐⭐⭐）**：
- **SRP 单一职责原则**：设计的**基础**
- **LSP 里氏代换原则**：实现OCP的**重要方式**
- **CRP 合成复用原则**：复用的**首选方式**

**重要（⭐⭐⭐）**：
- **LoD 迪米特法则**：设计的**指导原则**

**有用（⭐⭐）**：
- **ISP 接口隔离原则**：接口设计的**细化要求**

### ⚠️ 考点

**必背内容**：
1. 7个原则的中英文名称和缩写
2. 7个原则的一句话定义
3. 重要性排序（尤其是OCP和DIP的地位）

**记忆技巧**：
- 缩写：**S-O-L-I-D** + CRP + LoD
  - SOLID是Robert C. Martin提出的经典5原则
  - 加上CRP和LoD形成完整的7原则体系

## 🎯 本章总结

### 核心要点

1. **软件设计的层次**
   - 需求 → 规约 → 架构 → 设计
   - OOD处于"设计"层

2. **OOA/OOD/OOP的关系**
   - OOA：识别概念模型
   - OOD：添加技术细节（本课程重点）
   - OOP：编程实现

3. **为什么需要设计原则**
   - 糟糕设计的4个特征：僵硬、脆弱、复用率低、黏度高
   - 优秀设计的3个性质：可扩展、灵活、可插入
   - 设计原则是实现优秀设计的指南

4. **7个设计原则概览**
   - OCP和DIP是核心
   - 其他原则是基础或实现手段
   - 它们相互依赖、相互补充
