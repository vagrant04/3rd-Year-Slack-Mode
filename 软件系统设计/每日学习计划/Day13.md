## 一、软件产品线 Software Product Line (SPL)

### 1. 定义
软件产品线是一组软件密集型系统，共享一组通用的、可管理的特性集，满足特定市场或任务的特定需求，以规定的方式从一组核心资产开发而来。

### 2. SPL vs 单一产品架构（2015真题）

| 比较项 | 单一产品架构 | 产品线架构 |
|--------|-----------|----------|
| 目标 | 一个系统的质量属性 | 一组相关系统的共性和变化性 |
| 变化性 | 不是主要关注点 | 核心关注点（必须管理变化性） |
| 复用 | 偶尔复用 | 系统化、有计划的复用 |
| 架构范围 | 单一系统 | 整个产品族 |
| 投资回报 | 短期 | 长期（前期投入大，后期每个产品成本低） |

### 3. 变化性机制（Variability Mechanisms）

| 机制 | 说明 | 绑定时间 |
|------|------|----------|
| **Inclusion/Exclusion** | 包含或排除某些组件 | 构建时 |
| **Parameterization** | 通过参数控制行为 | 编译时/运行时 |
| **Inheritance** | 通过继承扩展基类 | 编译时 |
| **Template/Plugin** | 插件式扩展 | 运行时 |
| **Configuration** | 配置文件选择 | 部署时/运行时 |

### 4. SPL的两个关键过程
- **Core Asset Development（核心资产开发）**：开发可复用的共性资产
- **Product Development（产品开发）**：利用核心资产+变化性生成具体产品

## 二、架构基础概念

### 1. 软件架构的定义
> 一个程序或计算系统的软件架构是该系统的**结构**，包括软件**元素**、元素之间的**关系**，以及两者的**属性**。

### 2. 关键概念辨析

| 概念 | 英文 | 定义 |
|------|------|------|
| **Module（模块）** | Module | 实现单元，提供一组连贯职责的代码单位 |
| **Component（组件）** | Component | 运行时计算/数据存储的主要处理单元 |
| **Connector（连接器）** | Connector | 组件之间的交互通路 |
| **Element（元素）** | Element | 架构中的基本构建块（统称） |

### 3. Architecture vs Design vs Structure（重要区分！）

| 概念 | 含义 |
|------|------|
| **Architecture（架构）** | 系统的高层结构决策，影响质量属性，难以修改 |
| **Design（设计）** | 所有设计决策的集合，架构是设计的子集 |
| **Structure（结构）** | 系统的一种具体表现/视图，架构包含多个结构 |

**关系**：
- 每个系统有**一个**架构
- 但架构可以通过**多个结构（视图）**来展现
- 架构 ⊂ 设计（架构决策是设计决策中最重要的子集）
- 不是所有设计决策都是架构决策

### 4. 架构的影响来源（2015真题必考）

影响架构的因素：
1. **利益相关者(Stakeholders)**：不同角色有不同的质量关注
2. **开发组织**：团队结构影响架构（Conway's Law）
3. **技术环境**：可用的技术、框架、标准
4. **架构师的经验**：过去的成功/失败经验

**Architecture Influence Cycle（架构影响循环）**：
```
环境因素 → 架构 → 系统 → 反馈 → 环境因素
(利益相关者、组织、技术) → (设计决策) → (质量属性) → (经验积累)
```

## 三、需求如何影响架构（2025真题）

### 1. 不是所有需求都影响架构
- 大部分功能需求可以在任何架构中实现
- **质量属性需求**才是架构的主要驱动力
- **约束**（技术约束、业务约束）直接限制架构选择

### 2. 需求→架构的转化路径
```
需求 → ASR识别 → Utility Tree → ADD设计 → 架构
         ↑                                    ↓
    QAW (利益相关者)                        ATAM评估
```

## 四、Layered Pattern 补充（分层模式）

### 1. 关键特点
- **核心**：关注点分离（必须逐层访问，确定依赖关系）
- 每层为上层提供服务，使用下层的服务
- **Allowed-to-use关系**：只能使用下层（单向依赖）

### 2. 优缺点
**优点**：高内聚、松耦合、易于维护、层可独立替换

**缺点**：降低性能（层间调用开销）、级联修改（底层变化影响上层）

### 3. Layered的变体判断（考试考过）
- 如果形成**环形依赖**（A→B→C→A）：不是分层模式
- 如果允许**跳层访问**（A直接访问C，跳过B）：严格意义上不是分层，但实践中常见

## 五、MVC Pattern补充

### 1. 三个组件
- **Model（模型）**：应用数据和业务逻辑
- **View（视图）**：用户界面展示
- **Controller（控制器）**：处理用户输入，协调Model和View

### 2. 核心约束
- **Model不可以直接返回到Controller**（Model通过通知机制告知View变化）
- Model不依赖View和Controller
- View和Controller依赖Model

### 3. MVC优缺点
**优点**：耦合性低、重用性高、生命周期成本低、部署快、可维护性高

**缺点**：没有明确定义、不适合中小型应用、增加实现复杂度、视图和控制器过于紧密

## 六、软件产品线 vs MDA（Model-Driven Architecture）

| 比较项 | SPL | MDA |
|--------|-----|-----|
| 复用层次 | 架构+组件 | 模型 |
| 变化管理 | 变化性机制 | 模型转换 |
| 核心思想 | 产品族共性/变化性管理 | 平台无关模型→平台相关模型 |

### 1. 四种文档化视图类型
- Module Views（模块）
- C&C Views（组件连接器）

## 八、今日自测

1. 软件产品线和单一产品架构的核心区别？
   > SPL需要管理变化性，为整个产品族设计架构；单一产品只关注一个系统的质量属性。

2. Module、Component、Connector三者的区别？
   > Module是静态实现单元(代码)；Component是运行时处理单元；Connector是运行时组件间的交互通路。

3. 为什么说"架构 ⊂ 设计"？
   > 架构决策是设计决策的子集——是那些影响系统整体结构和质量属性的关键设计决策。

4. MVC中为什么Model不能直接调用Controller？
   > 为了保持Model的独立性和可复用性。Model通过通知机制(Observer模式)告知View变化。
