## 一、质量属性概述

### 1. 功能需求 vs 质量属性需求
- **功能需求**：系统做什么（What）
- **质量属性需求**：系统做得有多好（How well）
- 架构设计主要由质量属性驱动，而非功能需求

### 2. 七大质量属性
| 质量属性 | 英文 | 核心关注点 |
|----------|------|-----------|
| 可用性 | Availability | 系统故障时仍能提供服务 |
| 可修改性 | Modifiability | 修改的成本和风险 |
| 性能 | Performance | 响应时间、吞吐量 |
| 安全性 | Security | 机密性、完整性、可用性(CIA) |
| 可测试性 | Testability | 容易发现缺陷 |
| 易用性 | Usability | 用户完成任务的难度 |
| 互操作性 | Interoperability | 与其他系统交互的能力 |

## 二、质量属性场景（六要素）—— 每年必考！

### 通用质量属性场景的六个要素：

| 要素 | 英文 | 含义 | 示例 |
|------|------|------|------|
| **刺激源** | Source of Stimulus | 产生刺激的实体 | 用户、外部系统、内部组件 |
| **刺激** | Stimulus | 到达系统的事件 | 请求、故障、攻击、修改请求 |
| **环境** | Environment | 刺激发生时系统的条件 | 正常运行、过载、降级模式 |
| **制品** | Artifact | 被刺激的系统部分 | 服务器、进程、数据库 |
| **响应** | Response | 系统对刺激的活动 | 检测故障、恢复、处理请求 |
| **响应度量** | Response Measure | 可量化的响应指标 | 恢复时间、延迟、吞吐量 |

### 场景示例模板（考试直接套用）：
> 当 [刺激源] 在 [环境] 下对 [制品] 发出 [刺激] 时，系统的 [响应] 应满足 [响应度量]。

## 三、可用性 Availability（最高频考点）

### 1. 核心概念

**可用性公式**：
```
Availability = MTBF / (MTBF + MTTR)
```
- **MTBF** (Mean Time Between Failures)：平均无故障时间
- **MTTR** (Mean Time To Repair)：平均修复时间

**故障相关概念链**：
```
Fault(故障) → Error(错误) → Failure(失效)
  代码缺陷      内部状态异常     外部可观察的偏离
```

### 2. 可用性场景示例（2022真题原型）
> 当**硬件故障**（刺激）在**正常运行**（环境）下影响**主服务器**（制品）时，系统应**检测故障并切换到备份服务器**（响应），**停机时间不超过5分钟**（响应度量）。

### 3. 可用性策略（Tactics）

#### 检测故障 (Detect Faults)
| 策略 | 说明 |
|------|------|
| **Ping/Echo** | 定期发送探测包检测组件存活 |
| **Heartbeat（心跳）** | 组件定期发送"我还活着"的信号 |
| **Voting（投票）** | 多副本执行同一计算，多数决 |
| **Exception Detection** | 异常检测 |
| **Monitor** | 监控组件状态 |

#### 从故障恢复 (Recover from Faults)
| 策略 | 说明 |
|------|------|
| **Active Redundancy（主动冗余/热备）** | 所有备份同时处理，故障时无缝切换 |
| **Passive Redundancy（被动冗余/温备）** | 备份定期同步状态，故障时接管 |
| **Spare（冷备）** | 备份空闲，故障时启动并加载状态 |
| **Rollback（回滚）** | 恢复到上一个正确状态（Checkpoint） |
| **Retry（重试）** | 假设故障是暂时的，重新尝试 |

#### 防止故障 (Prevent Faults)
| 策略 | 说明 |
|------|------|
| **Service Removal（服务摘除）** | 暂时移除有问题的服务进行修复 |
| **Transactions（事务）** | 确保操作的原子性 |
| **Predictive Model** | 预测可能的故障提前处理 |
| **Exception Prevention** | 通过设计避免异常发生 |

## 四、可修改性 Modifiability

### 1. 核心关注
- 修改什么？（功能、平台、质量属性、容量）
- 谁来修改？（开发者、用户、管理员）
- 修改何时发生？（设计时、编译时、构建时、运行时）
- 修改的成本和风险如何？

### 2. 可修改性场景示例
> 当**开发者**（刺激源）希望在**设计时**（环境）对**UI模块**（制品）添加**新的支付方式**（刺激）时，修改应**在2人周内完成且不影响其他模块**（响应度量）。

### 3. 可修改性策略

#### 减小模块大小 (Reduce Size of Module)
| 策略 | 说明 |
|------|------|
| **Split Module（拆分模块）** | 将大模块拆为小模块，减少单次修改影响范围 |

#### 增加内聚 (Increase Cohesion)
| 策略 | 说明 |
|------|------|
| **Increase Semantic Coherence** | 确保模块内元素都为同一目的服务 |

#### 减少耦合 (Reduce Coupling)
| 策略 | 说明 |
|------|------|
| **Encapsulate（封装）** | 通过接口隐藏实现细节 |
| **Use an Intermediary（中间件）** | 引入中间层切断直接依赖 |
| **Restrict Dependencies（限制依赖）** | 减少模块间的依赖关系 |
| **Abstract Common Services** | 抽象公共服务 |

#### 延迟绑定 (Defer Binding)
| 策略 | 说明 |
|------|------|
| **Runtime Registration** | 运行时注册（如Plugin机制） |
| **Configuration Files** | 通过配置文件修改行为 |
| **Polymorphism** | 多态实现运行时绑定 |
| **Component Replacement** | 组件热替换 |
| **Publish-Subscribe** | 发布订阅实现松耦合绑定 |

## 五、性能 Performance

### 1. 核心关注
- **响应时间(Latency)**：从请求到响应的时间
- **吞吐量(Throughput)**：单位时间处理的请求数
- **资源利用率**：CPU、内存、网络的使用情况

### 2. 性能场景示例
> 当**1000个并发用户**（刺激源）在**正常负载**（环境）下向**Web服务器**（制品）发送**页面请求**（刺激）时，系统应**在2秒内返回结果**（响应度量），且**平均延迟不超过200ms**。

### 3. 性能策略

#### 控制资源需求 (Control Resource Demand)
| 策略 | 说明 |
|------|------|
| **Manage Sampling Rate** | 降低采样率减少处理量 |
| **Limit Event Response** | 限制事件响应频率 |
| **Prioritize Events** | 事件优先级排序 |
| **Reduce Overhead** | 减少中间件开销 |
| **Bound Execution Times** | 限制执行时间 |
| **Increase Resource Efficiency** | 提高算法效率 |

#### 管理资源 (Manage Resources)
| 策略 | 说明 |
|------|------|
| **Increase Resources** | 增加硬件资源 |
| **Introduce Concurrency** | 引入并发/并行处理 |
| **Maintain Multiple Copies（副本）** | 数据/计算副本（负载均衡） |
| **Schedule Resources** | 资源调度策略（FIFO、优先级等） |

## 六、Tactics vs Patterns 的关系

**重要概念**：
- **Tactics（策略）**：单一设计决策，影响单个质量属性的控制
- **Patterns（模式）**：多个策略的打包组合，解决更完整的问题

**关系**：
- 一个Pattern通常包含多个Tactics
- Tactics是构建Pattern的"砖块"
- 例：Active Redundancy(Tactic) 是构成 高可用集群(Pattern) 的一部分

   > 前者减少工作量（不做/少做），后者增加处理能力（做得更快/更多）。
