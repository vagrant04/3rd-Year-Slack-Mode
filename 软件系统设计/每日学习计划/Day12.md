## 一、SOA（面向服务架构）

### 1. 定义
SOA是一种软件设计风格，其服务通过应用程序组件，通过网络上的通信协议提供给其他组件。

**核心原则**：服务独立于供应商、产品和技术。

### 2. SOA的组成元素

| 元素类型 | 说明 |
|---------|------|
| **Service Provider（服务提供者）** | 提供一个或多个服务，通过发布的接口 |
| **Service Consumer（服务消费者）** | 调用服务，可直接或通过中间件 |
| **ESB（企业服务总线）** | 路由服务间信息，进行数据转换 |
| **Service Registry（服务注册中心）** | 服务注册和发现 |
| **Orchestration Engine（编排引擎）** | 协调服务消费者与提供者的交互 |

### 3. SOA连接器（Connector）
- **SOAP**：基于HTTP的XML消息交换
- **REST**：基于HTTP四操作（GET/POST/PUT/DELETE）
- **Asynchronous Messaging**：异步消息传递（即忘即发）

### 4. SOA实现原则（重要！）
| 原则 | 含义 |
|------|------|
| 服务契约 | 服务按描述文档的契约行事 |
| 服务封装 | 隐藏实现逻辑 |
| 服务重用 | 逻辑分布在不同服务中提高重用性 |
| 服务组合 | 一组服务可以协调工作，组合业务需求 |
| 服务自治 | 服务对所封装的逻辑具有控制权 |
| 服务无状态 | 服务将活动所需保存的资讯最小化 |

### 5. SOA优缺点
**优点**：高内聚、松耦合、互操作性好、开放标准、模组化高可用性、动态识别/注册/调用

**缺点**：构建复杂、难以测试验证、各独立服务演化不可控、中间件可能成为性能瓶颈

## 二、微服务（Microservices）

### 1. 定义
微服务是**分布式架构，SOA的一种扩展**。将单一应用开发为一组小型服务，每个服务运行在自己的进程中，通过轻量级通信机制（通常HTTP REST）交互。

### 2. 微服务的特点（2025真题！必背）

| 特点 | 说明 |
|------|------|
| **通过服务组件化** | 组件=可独立替换/升级的软件单元，服务=进程外的组件 |
| **围绕业务能力组织** | 按业务功能（而非技术层）划分团队和服务 |
| **产品而非项目** | 团队全生命周期负责服务（"you build it, you run it"） |
| **智能端点和哑管道** | 服务自身包含逻辑，通信通道尽可能简单(REST/消息队列) |
| **去中心化治理** | 每个服务可选择适合的技术栈 |
| **去中心化数据管理** | 每个服务拥有自己的数据库 |
| **基础设施自动化** | CI/CD、自动化测试、自动化部署 |
| **为失效而设计** | 容错设计，服务可能随时失效 |
| **演化式设计** | 服务可独立部署和演化 |

### 3. 构建云原生应用(SaaS)的12要素
1. **基准代码**：一份代码，多份部署
2. **依赖**：显式声明依赖关系
3. **配置**：存储于环境变量中
4. **后端服务**：视为附加资源
5. **构建、发布、运行**：严格区分三个步骤
6. **进程**：以无状态进程运行
7. **端口绑定**：通过端口绑定提供服务
8. **并发**：通过进程模型扩展
9. **易处理**：快速启动和优雅终止
10. **开发环境与线上环境等价**：尽可能保持一致
11. **日志**：视为事件流
12. **管理进程**：后台管理任务作为一次性进程运行

### 4. SOA vs Microservices

| 比较项 | SOA | Microservices |
|--------|-----|---------------|
| 服务粒度 | 较粗（企业级服务） | 较细（单一业务功能） |
| 通信 | ESB（重量级） | REST/消息队列（轻量） |
| 数据管理 | 可能共享数据库 | 每服务独立数据库 |
| 治理 | 集中化（统一标准） | 去中心化（各服务自选） |
| 部署 | 通常打包部署 | 独立部署 |
| 典型技术 | SOAP, WS-*, ESB | REST, Docker, K8s |

## 三、Broker Pattern（代理模式-架构层面）

### 1. 定义
Broker模式用于构建分布式软件系统，代理组件负责协调通信（转发请求、传输结果和异常）。

### 2. 上下文
多个同步或异步交互的远程对象组成的系统。

### 3. 元素
| 元素 | 职责 |
|------|------|
| **Client** | 服务请求者 |
| **Server** | 服务提供者 |
| **Broker** | 定位合适的服务器，转发请求，返回结果 |
| **Client-Side Proxy** | 管理客户端与Broker的通信（编组/解组） |
| **Server-Side Proxy** | 管理服务器与Broker的通信 |
| **Bridge** | 桥接不同Broker之间的通信 |

### 4. 优缺点
**优点**：Client和Server解耦、提高可伸缩性和可扩展性、大集群QPS提高

**缺点**：增加前期复杂度、可能成为通信屏障/瓶颈、可能成为安全攻击目标、难以测试

### 5. Broker与Client-Server的对比
- Broker存在于Client和Server之间，可动态改变关系
- C-S模式关系相对固定，没有broker
- C-S不采用broker可能导致请求被拦截
- Broker提高互操作性，但增加复杂度

## 四、Pipe-and-Filter Pattern（管道-过滤器）

### 1. 定义
管道和过滤器模式应用在顺序处理结构中，一系列filter体现依赖关系。

### 2. 元素
- **Filter（过滤器）**：相当于Component，起数据处理/计算作用，有input和output
- **Pipe（管道）**：相当于Connector，连接filter，将output导入下一个filter的input

### 3. 约束
- 连接的filter必须在数据类型上达成一致
- filter只依赖于前一个filter的输出
- 不适合交互式系统（破坏依赖关系）

### 4. Java实现考点（2021真题编程题）
```java
interface Filter {
    String process(String input);
}
class UpperCaseFilter implements Filter {
    public String process(String input) { return input.toUpperCase(); }
}
class TrimFilter implements Filter {
    public String process(String input) { return input.trim(); }
}
class Pipeline {
    private List<Filter> filters = new ArrayList<>();
    public void addFilter(Filter f) { filters.add(f); }
    public String execute(String input) {
        String result = input;
        for (Filter f : filters) { result = f.process(result); }
        return result;
    }
}
```

## 五、2025设计题示例：外卖平台微服务设计

**题目**：用微服务架构设计外卖平台。

**参考答案要点**：
1. **服务划分**（围绕业务能力）：
   - 用户服务（注册、登录、个人信息）
   - 商家服务（菜单管理、营业状态）
   - 订单服务（下单、状态追踪）
   - 支付服务（支付、退款）
   - 骑手服务（接单、配送追踪）
   - 评价服务（评分、评论）

2. **通信方式**：REST API + 消息队列（订单状态变更通知）

3. **数据管理**：每个服务独立数据库

4. **关键质量属性**：
   - 可用性：服务冗余部署，故障隔离
   - 性能：缓存热门商家和菜单数据
   - 可修改性：服务独立部署和升级
