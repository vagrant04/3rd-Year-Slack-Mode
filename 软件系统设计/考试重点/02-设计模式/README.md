## 3. 设计模式部分 50%

### 3.1 七大面向对象设计原则

#### SRP 单一职责原则

定义：

- 一个类只负责一个职责，且这个职责应被完整封装。

考点：

- 职责越多，变化原因越多，类越不稳定。

#### OCP 开闭原则

定义：

- 软件实体应对扩展开放，对修改关闭。

实现方式：

- 抽象。
- 多态。
- 接口。
- 组合。
- 工厂方法、策略模式等。

#### LSP 里氏代换原则

定义：

- 所有引用基类的地方必须能透明地使用其子类对象。

和 OCP 的关系：

- LSP 是 OCP 的具体保障。只有子类能安全替换父类，系统才可通过新增子类扩展而不修改原代码。

#### DIP 依赖倒转原则

定义：

- 高层模块不应依赖低层模块，二者都应依赖抽象。
- 抽象不应依赖细节，细节应依赖抽象。
- 面向接口编程，而不是面向实现编程。

在模式中的体现：

- Strategy：Context 依赖 Strategy 接口。
- Factory Method：客户端依赖抽象工厂/抽象产品。
- Observer：Subject 依赖 Observer 接口。
- Command：Invoker 依赖 Command 接口。

#### ISP 接口隔离原则

定义：

- 客户端不应依赖它不需要的接口。

考点：

- 大接口应拆成多个小接口，避免“胖接口”。

#### CRP 合成复用原则

定义：

- 优先使用组合/聚合，而不是继承。

考点：

- 组合运行时更灵活，继承编译时固定、耦合更强。

#### LoD 迪米特法则 / 最小知识原则

定义：

- 一个对象应尽量少了解其他对象。

在模式中的体现：

- Facade：给复杂子系统提供统一入口。
- Mediator：对象不直接通信，通过中介者协调。

### 3.2 设计模式基本概念

设计模式是什么：

- 在特定上下文中，对反复出现的一类设计问题的通用解决方案。
- 通常包含：模式名称、问题、解决方案、效果。

按目的分类：

1. Creational 创建型：关注对象创建。
2. Structural 结构型：关注类或对象组合。
3. Behavioral 行为型：关注对象交互和职责分配。

按范围分类：

1. Class Pattern：通过继承处理类与子类关系，编译时确定。
2. Object Pattern：处理对象之间关系，运行时更动态。

### 3.3 策略模式 Strategy

意图：

- 定义一系列算法，把它们封装起来，并使它们可以相互替换。

结构：

- Context：上下文，持有 Strategy。
- Strategy：策略接口。
- ConcreteStrategy：具体策略。

适用场景：

- 多个算法可互换。
- 需要在运行时选择算法。
- 想消除大量 if-else。
- 算法细节需要对客户端隐藏。

体现原则：

- SRP：每个策略类只负责一个算法。
- OCP：新增策略不改 Context。
- DIP：Context 依赖 Strategy 抽象。
- CRP：Context 组合 Strategy。

常考设计题：

- 飞行模拟软件不同飞机飞行方式。
- 买票系统不同角色折扣。

### 3.4 工厂方法 Factory Method

意图：

- 定义创建对象的接口，让子类决定实例化哪个类。

适用：

- 客户端不应依赖具体产品类。
- 创建逻辑需要延迟到子类。
- 新增产品时希望少修改已有代码。

如何体现 OCP：

- 新增产品时，增加具体产品和具体工厂即可，不需要修改抽象工厂和客户端。

### 3.5 抽象工厂 Abstract Factory

意图：

- 提供创建一系列相关或相互依赖对象的接口，而无需指定具体类。

适用：

- 系统需要产品族。
- 一组产品需要一起使用。
- 希望切换整套风格/平台。

如何体现 OCP：

- 新增产品族时，只需新增具体工厂和一组具体产品。

局限：

- 新增产品等级结构时，要修改抽象工厂接口，违反 OCP。

工厂方法 vs 抽象工厂：

- 工厂方法：创建一种产品，靠继承延迟实例化。
- 抽象工厂：创建一族产品，强调产品族一致性。

### 3.6 单例 Singleton 与 Multi-instance

Singleton：

- 保证一个类只有一个实例，并提供全局访问点。

考点：

- 私有构造方法。
- 静态实例。
- 静态访问方法。
- 线程安全。

Multi-instance：

- 单例的推广，限制实例数量不超过常量 n。

### 3.7 原型 Prototype 与享元 Flyweight

原型模式：

- 创建型模式。
- 通过复制已有对象创建新对象。
- 复用的是创建过程。

享元模式：

- 结构型模式。
- 通过共享细粒度对象减少内存。
- 复用的是对象实例。

常考点：

- 为什么 Prototype 是创建型，而 Flyweight 是结构型？

### 3.8 命令模式 Command

意图：

- 将请求封装为对象，使请求调用者和请求接收者解耦。

角色：

- Command：抽象命令。
- ConcreteCommand：具体命令。
- Invoker：调用者。
- Receiver：接收者。
- Client：创建命令并绑定接收者。

适用：

- 需要撤销/重做。
- 需要命令队列。
- 需要日志记录。
- 需要宏命令。
- 需要解耦按钮/菜单等调用者和实际业务对象。

为什么 Invoker 不能去掉：

- Invoker 管理命令执行时机、队列、历史、撤销栈。
- 去掉后职责会混入 Client 或 Receiver，违反 SRP，也降低扩展性。

### 3.9 观察者模式 Observer

意图：

- 定义对象之间一对多依赖，当一个对象状态变化时，所有依赖者自动收到通知。

角色：

- Subject。
- ConcreteSubject。
- Observer。
- ConcreteObserver。

Push vs Pull：

- Push：Subject 推送详细数据。
  - 优点：及时，Observer 直接获得数据。
  - 缺点：Subject 需要知道 Observer 需要什么，耦合更高，可能传无用数据。
- Pull：Subject 只通知变化，Observer 自行拉取数据。
  - 优点：Observer 按需获取，解耦更好。
  - 缺点：可能多次查询，效率较低，Observer 需要知道 Subject 接口。

Java notifyObservers 两种重载：

- `notifyObservers()`：Pull。
- `notifyObservers(Object arg)`：Push。

常考设计题：

- 分布式缓存同步。
- 游戏角色死亡通知。
- 学校/公司层级通知系统。
- 多渠道通知系统。

### 3.10 组合模式 Composite

意图：

- 将对象组合成树形结构，让客户端一致地处理单个对象和组合对象。

角色：

- Component。
- Leaf。
- Composite。

适用：

- 部分-整体层次结构。
- 希望客户端忽略单个对象和组合对象差异。

常考设计题：

- 大学通知系统：学校/院系/班级/个人。
- 公司通知系统：公司/部门/员工。
- 组合命令：MacroCommand。

### 3.11 状态模式 State

意图：

- 允许对象在内部状态改变时改变行为，看起来像改变了类。

结构：

- Context。
- State。
- ConcreteState。

状态模式 vs 策略模式：

- 状态模式：状态转换通常由状态对象内部控制，强调对象生命周期和状态迁移。
- 策略模式：策略通常由客户端/外部选择，强调算法可替换。

### 3.13 桥接 Bridge 与装饰者 Decorator

Bridge：

- 将抽象部分和实现部分分离，使二者可以独立变化。
- 适合多维变化，例如遥控器类型和设备类型分别变化。

Decorator：

- 动态给对象添加职责。
- 比继承更灵活，符合 CRP。

区别：

- Bridge 主要为了解耦两个独立变化维度。
- Decorator 主要为了动态叠加功能。

### 3.14 外观 Facade 与代理 Proxy

Facade：

- 给复杂子系统提供统一高层接口。
- 目的：简化访问。
- 面对：一组对象/子系统。
- 体现：迪米特法则。

Proxy：

- 为另一个对象提供代理，以控制对该对象的访问。
- 目的：控制访问。
- 面对：一个对象。
- 例子：远程代理、虚拟代理、保护代理。

常考题：

- 外观满足什么原则？
- 外观和代理的区别。

### 3.15 MVC 与设计模式

MVC：

- Model：业务数据和业务逻辑。
- View：展示和用户界面。
- Controller：处理用户输入，协调 Model 和 View。

MVC 中可能用到的设计模式：

- Observer：Model 变化通知 View。
- Strategy：Controller 对不同输入采用不同响应策略。
- Composite：组合多个 View。

优点：

- 低耦合。
- 可维护性高。
- 视图和业务逻辑分离。

缺点：

- 实现复杂度增加。
- 小系统中可能过度设计。

### 3.16 防御式编程、断言、错误处理

防御式编程：

- 预见可能错误，通过检查、约束、隔离等方式防止错误扩大。

断言：

- 开发期间使用，用于检查程序内部不变量。
- 不应有副作用。
- 用来发现程序员错误。

错误处理：

- 面向可预期的外部错误，如用户输入错误、网络失败、文件不存在。

Barricade：

- 在系统边界设置“路障”，外部不可信数据进入系统前先验证和清洗。
